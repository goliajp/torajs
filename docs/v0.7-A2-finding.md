## Root cause

`__torajs_libc_malloc(size)` path adds **~10-30 ns per alloc** vs libc
nano-allocator thread-cache fast-path:

```
__torajs_libc_malloc(size):              libc malloc (libsystem_malloc nano):
  1. total = size + 16   ← SHIM_HEADER     1. thread-cache LIFO pop  ← 2-3 cyc
  2. raw = __torajs_malloc(total)             (return: 1 cache line)
        ← size-class free-list lookup
        ← (atomic linked list pop)
  3. *raw = total        ← header store
  4. return raw + 16
```

Two sub-costs:

1. **SHIM_HEADER 16B prepend** — pure overhead; the size info is needed
   only by `__torajs_libc_free` because libc API doesn't carry size, but
   torajs IR code paths often *know* the size statically.
2. **size-class lookup vs thread-cache** — even after SHIM_HEADER is
   amortized, the free-list pop is on a global structure; libc nano has
   per-thread LIFO with cycle-counted fast-path.

Math check: `generic-pair-1m` alloc per iter × 1e6 iter × 20 ns delta =
+20 ms — observed +4.9 ms is within that envelope (other costs share the
hot loop). Hypothesis stands.

## Why JIT (`torajs-run`) doesn't regress

`torajs-run` runs IR in-process via inkwell JIT in the cli binary. Both
JIT and AOT paths use the **same** mmalloc symbols (link-resolved in cli
binary at JIT time). But JIT mode's overall run_ms is dominated by IR
compile cost (~150 ms typical), drowning the per-alloc shim delta into
noise; AOT-built binary has zero JIT overhead so the alloc delta surfaces
cleanly.

This is not a contradiction — both paths *are* slower per-alloc; only AOT
shows it in measurement because AOT wall-clock has nothing else dominant.

## Fix path — metal-tier allocator redesign (textbook answer, not patch-on-shim)

The original triage listed three options as if they were alternatives. They
are not. **All three are required**, and the union is itself a sub-set of
the textbook metal-tier allocator design (Go runtime malloc, mimalloc,
snmalloc, jemalloc). Patch-on-shim hits the noise floor of libc nano while
leaving the structural ceiling capped. The fix is to redesign mmalloc to
the published textbook shape, against which libc nano is itself a tradeoff
artifact (libc ABI forces shape constraints that a self-controlled allocator
shouldn't accept).

### The target shape — span-based + per-thread cache + per-CPU sharding

Cribbed from Go's `mheap` / `mcache` / `mcentral` triad, mimalloc's per-CPU
heap, snmalloc's slab-based design. Same playbook every state-of-the-art
allocator uses; **not novel — that's the point** (正统 pillar).

```
                  ┌─────────────────────────────────────────────┐
                  │  mmap arena (2 GB span pool, on-demand grow)│
                  └──────────────────┬──────────────────────────┘
                                     │ 64 KB span allocations
                  ┌──────────────────┴──────────────────────────┐
                  │  Span registry (1 entry per 64 KB span)     │
                  │  Per-span metadata: size_class, allocator   │
                  │    (free bitmap | freelist head), ref_count │
                  │  → ptr → span lookup is O(1) (mask + shift) │
                  │  → size from span metadata, NOT per-alloc header │
                  └──────────────────┬──────────────────────────┘
                                     │
   ┌─────────────────────────────────┴──────────────────────────┐
   │                                                             │
   │  Size-class allocator (32 classes, 16 B .. 32 KB)           │
   │    each class = pool of spans, each span split into N slots │
   │    free → push slot to local TLAB free list                 │
   │    alloc → pop slot from local TLAB (zero atomic ops)       │
   │                                                             │
   └────┬──────────────────────┬────────────────────┬───────────┘
        │                      │                    │
   ┌────▼────┐            ┌────▼────┐          ┌────▼────┐
   │ TLAB #0 │   TLABs    │ TLAB #1 │  ...     │ TLAB #N │  one per thread
   │ free    │   per      │ free    │          │ free    │  cache
   │ list ×  │  thread    │ list ×  │          │ list ×  │  (cycle-cost
   │ 32 cls  │            │ 32 cls  │          │ 32 cls  │   = libc nano)
   └────┬────┘            └────┬────┘          └────┬────┘
        │ refill when empty   │                    │
        └─────────┬───────────┴────────────────────┘
                  │ atomic batch-pull (16 slots/op)
   ┌──────────────▼────────────────────────────────────────────┐
   │  Per-CPU central queue (snmalloc / mimalloc pattern)      │
   │    lock-free MPMC for cross-thread frees                  │
   │    avoids global mutex; sharded by current_cpu()          │
   └──────────────┬────────────────────────────────────────────┘
                  │ refill from span pool
                  ▼
              [back to span registry]

Large allocs (> 32 KB):
  direct mmap, registered in span registry with size_class = LARGE,
  freed via munmap directly. No slot/freelist overhead.

API surface (3 layers):

  Layer 0 — pub fn alloc(size: usize) -> *mut u8
            pub fn free(ptr: *mut u8)
            (size derived from span lookup; no header anywhere)

  Layer 1 — pub fn alloc_sized(size: usize) -> *mut u8     ← caller knows size
            pub fn free_sized(ptr: *mut u8, size: usize)   ← skips span lookup
            (cycle-fewer fast path; IR emits this when size is static)

  Layer 2 — pub extern "C" __torajs_libc_malloc(size) → ptr+16  ← libc-compat shim
            pub extern "C" __torajs_libc_free(ptr)              ← reads SHIM_HEADER
            (only used by external C consumers, not by torajs sub-crates;
             once all sub-crates migrate to Layer 0/1, this layer deletes)
```

This design **simultaneously incorporates** what was previously listed as
Options 1, 2, 3 — and goes further:

- "Option 1" (direct sized alloc) = Layer 1 API in this shape; IR call-site
  routing.
- "Option 2" (thread-local cache) = TLAB row above; **not deferred**, shipped
  in the same redesign because the design is incoherent without it (without
  TLAB the size-class allocator is just a slower libc-compat shim).
- "Option 3" (8B header) = becomes **0B header** in Layer 0/1; size info
  moves to span metadata. SHIM_HEADER survives only in Layer 2, which itself
  ships only as long as external C consumers exist.

### Thread safety from day 1

Single-thread limitation is a current artifact of the runtime, not a target.
Per `roadmap.md` post-v1.0 path includes worker threads; the allocator
**ships thread-safe from this redesign**. Per-CPU sharding + lock-free MPMC
free queue (atomic linked list with CAS-based push, batch pop) is the
mimalloc/snmalloc playbook — no design decision to make, just implementation.

Single-threaded callers pay zero contention cost (TLAB pop is a non-atomic
load+store); cross-thread frees go through the per-CPU queue. The cost of
adding thread safety later is enormous; the cost of adding it now is one
extra atomic op on the cold path. **上限优先 — design once at the ceiling**.

### What this kills

- SHIM_HEADER per-alloc overhead → gone (Layer 0/1; survives only in Layer 2)
- size-class lookup atomic ops → gone (TLAB is non-atomic local)
- per-CPU contention on free → gone (sharded MPMC queue)
- the "patch on shim" mental model → gone (Layer 2 is the explicit
  external-C compatibility surface, not the primary path)
- the "ROI defers TLAB" framing → gone (TLAB is required for the design to
  cohere, not optional)

### Reference implementations (正统 — read these first, don't invent)

| Paper / source | What to crib |
|---|---|
| Go runtime `src/runtime/malloc.go` + `mcache.go` + `mcentral.go` + `mheap.go` | mcache/mcentral/mheap triad; size class table (67 classes); large-alloc → direct mheap. textbook reference. |
| mimalloc paper (Leijen et al., MSR 2019) + source | Per-thread page lists; "extreme polished" small-object path; sharding via thread-id mod N. |
| snmalloc (Microsoft) | Per-CPU heap; lock-free remote dealloc queue; chunk-based slab allocator. |
| jemalloc src/arena.c | Original per-CPU arena design (predates snmalloc); benchmark target. |
| `tcmalloc` (Google) | TLAB sizing strategy; spare-size class for "between class N and N+1" requests. |

Pick mimalloc's design philosophy (smallest core + cleanest invariants) as
the base; integrate Go's size class table (battle-tested for JS-like
workloads) and snmalloc's per-CPU sharding.

## Trigger upgrade — raise audit bar, raise numeric target

Two changes to the A2 → A3 L4 trigger. **Both raise the bar; neither lowers
it.** Proposal applied here for takagi formal sign-off (L4 changes are
takagi's decision per 4-layer rules); the rationale is textbook (audit
discipline = main path) so the sign-off is the formality, not the question.

### Change 1 — raise numeric target above baseline (not parity)

Old gate (status memory L4):

> bench geomean ±5% no regression vs `ab0b7fe` baseline

Replaced by:

> bench geomean torajs vs rust ≥ **1.60×** AND torajs vs bun-aot ≥ **4.10×**

Baseline values are 1.539× and 4.030×. The new gate requires the redesign
to **exceed baseline** (~4% uplift on each axis), not just recover it.
Rationale: the metal-tier redesign (span + TLAB + per-CPU) is documented
in mimalloc/snmalloc papers to deliver 15-40% over libc nano on alloc-heavy
workloads. Recovering baseline parity would mean we shipped a redesign that
only neutralized its own regression — that is not 上限优先, that is
patch-on-shim with extra steps. The +4% gate is the floor; the actual
expected delivery is +15-40% on alloc-heavy cases.

If validation lands below the floor, **the redesign itself is wrong**
(missed a constant, picked the wrong size class table, mis-implemented
TLAB refill). Stop and audit; do not lower the gate.

### Change 2 — add audit-documented alternative branch

Old gate is a single numeric condition. Replaced by union:

> (numeric gate as Change 1) **OR** audit + root-cause documented in
> `docs/v0.7-A{n}-finding.md` + picked fix shipped in substrate commit(s) +
> re-bench confirms a revised ≥-baseline gate against a new baseline
> acknowledged in the finding doc, with finding doc revised to ✅ closed.

Rationale: without an audit-documented alternative, a trigger could plateau
indefinitely if a redesign survives multiple fix attempts. The alternative
**raises the audit bar** (must document root cause + ship a fix + revalidate
with explicit new baseline) and explicitly forbids lowering the numeric gate
without audit — violating `memory/feedback_no_trigger_lowering.md` ("base
infra project, never lower triggers") is the failure mode this guards.

Same property mailrs's "negative-result documented" branch buys for v0.1
(where bench infra was the actual blocker and a 6-month rebuild path would
have stranded v0.2+) — adapted here to "fix-shipped-and-validated" form
because torajs's blocker is a known fix path, not an infra gap.

### Application

Both changes apply atomically to status memory L4 when this finding doc
is committed (or earlier on takagi's word). They do not affect A1 trigger
(already met) and they tighten A2 → A3 only.

### Prod panic-site audit across all 16 staticlibs

Manual `grep` for `panic!() / .expect() / .unwrap() / assert!() / todo!() /
unreachable!() / unimplemented!()` across `crates/torajs-{16 staticlibs}/src/`,
excluding `#[cfg(test)] mod tests { }` inline blocks. Of the 1129 raw hits,
**all 25 surviving "prod" sites turned out to be `#[cfg(test)] fn` test
stubs** (cross-tier extern stubs for cargo unit tests, e.g.
`#[cfg(test)] pub unsafe extern "C" fn __torajs_rc_inc(_p) { panic!(...) }`
in `torajs-promise/src/lib.rs:67-115`). These do NOT enter the release
staticlib because the `#[cfg(test)]` gate is off in `cargo build --release`.

So the panic infra **is not pulled by any explicit prod panic site we own**.
It's pulled by:

1. **`fmt::write` / `Debug` formatting machinery** — used by `panic!` message
   formatter and by any `format!`/`write!` in the std code we transitively
   link (e.g. `Vec::push` may format on capacity overflow panic message).
2. **`std::path` / `std::fs` / `std::backtrace_rs`** — pulled by Rust's
   default `panic_handler` which generates a stderr-formatted backtrace
   with file:line for each frame. Even when `panic = "abort"` runs the
   message formatter and reaches the handler before aborting.
3. **`std::thread::Thread::new`** — pulled by `thread_local!` storage init
   which sub-crates use (e.g. cycle collector + microtask queue + throw
   slot). `thread_local!` macro expansion wires `Thread::current()` for
   diagnostic naming.
4. **`core::slice::sort`** — pulled transitively by `std::backtrace_rs`
   when sorting symbol-resolution candidates.

Conclusion: the panic tree is **not removable by source-level panic-site
replacement** — there are no explicit sites left. Removing it requires
replacing the std default panic infrastructure itself (the `panic_handler`
+ formatter trees), or eliminating panic message formatting at compile
time via `panic_immediate_abort`.

### 9b strategy (substrate work; ship in a separate commit per autorun-pipeline)

**Known history — polish A4 / B2 (2026-05-24):**

- Polish A4 (`df75d25`) added `-Cpanic=immediate-abort` for **−91% size win**
  (fib40 445 KB → 38 KB). All panic call sites compiled down to inline
  `abort` (`ud2`); demangle + backtrace + std::path trees all DCE'd.
- B2 diagnosis revealed **+19% geomean perf regression** across 16/26 bench
  cases (throw-catch-100k +149%, promise-all-1k +86%, async-fn-call +43%,
  fifo-queue +42%, closure-counter +33%). Root cause: `immediate-abort`
  inlines `abort()` at every panic edge, changing LLVM's hot-path layout +
  register allocation away from the cold-call-with-PGO pattern.
- Polish A4.1 (`scripts/release-build.sh`) reverted to `build-std + panic_abort`
  WITHOUT `immediate-abort`: kept the **−14% perf-neutral win** (unwind
  metadata gone), dropped the **−77% additional size win** (text panic
  tree stays).

So Step 9b cannot simply "re-enable `immediate-abort`" — the 2026-05-24
ship cycle proved this is **HARD-rejected by perf gate** (`feedback_perf_priority`
+ design pillar #1 "performance-first"). Strip the demangle/backtrace
trees by other means.

**Three candidate paths** (each ships as a separate substrate commit):

**Path A — Custom `#[panic_handler]` in torajs-panic that skips backtrace+demangle.**
The standard `panic_handler` is what pulls `rustc_demangle::demangle`
(22.4 KiB) and `std::backtrace_rs::symbolize::gimli` (49.0 KiB). A
custom handler that just `write(stderr, panic_info.message_bytes)` +
`abort()` short-circuits the whole tree. `torajs-panic` crate exists
(empty staticlib; `target/release/libtorajs_panic.a` is the staticlib
slot for this). Wire it as the global panic_handler via either (i) a
custom panic_runtime crate (the formal way, requires `#![feature(panic_runtime)]`
+ `#![panic_runtime]` attr), or (ii) `#[panic_handler]` in the user
binary's entry crate (simpler but conflicts with build-std's panic_abort
runtime). Expected: **−75 to −100 KiB** (demangle + backtrace + std::path
trees gone). Risk: must not break panic message visibility for genuine
runtime errors (e.g. mmalloc OOM); the custom handler's message should
still reach stderr.

**Path B — Replace `std::thread_local!` with custom TLS init that doesn't
pull `Thread::new`.** `Thread::new` is 19.6 KiB. Sub-crates use
`thread_local!` for cycle collector / microtask queue. macOS has
`pthread_key_create` for TLS — a torajs-syscall layer over it (or `#[thread_local]`
attribute, already used in mmalloc TLAB) skips `std::thread`. Expected:
**−20 KiB**. Risk: changes TLS init order; needs careful per-TLS audit.

**Path C — `function-sections` codegen + `-Wl,-dead_strip` linker.**
Compile each staticlib with `-Cforce-frame-pointers=no -Csymbol-mangling-version=v0
-Zfunction-sections=true`, then macOS clang's implicit `-dead_strip` (or
explicit `-Wl,-dead_strip_dylibs`) will DCE per-symbol instead of
per-cgu. Expected: strips the 12 dead torajs helpers (4.4 KiB) AND any
std::path / std::fs subtree that's not transitively reachable from main.
**−10 to −60 KiB** (size win depends on actual unreached-fn count after
LTO).

**Order**: Path C first (cheapest substrate change; just RUSTFLAGS + linker
flags; no source changes; ship as a single commit). Then Path A (more
involved; needs torajs-panic wire-up). Path B last (lowest payoff per
LOC). Path A is the highest-leverage single change but also riskiest.

**Cumulative target**: 345 KiB polish-A4.1 baseline → (A) ≤ 270 → (C) ≤ 240
→ (B) ≤ 220 KiB. Step 9c+9d must then close the final 20-25 KiB to hit
the Step 10 ≤ 200 KiB trigger.

### Step 9b experiment 1 results (2026-05-27, no commit)

Tested two intuitive but ineffective approaches before locking the
custom panic_runtime path:

**1. `-Zfunction-sections=y` on the polish-A4.1 build path** — Hypothesis:
finer-grained sections let `-Wl,-dead_strip` DCE per-fn instead of

geomean numbers).

**2. `get_unchecked` replacement of 6 `[i]` indexing sites** in
`torajs-str/src/pool.rs` (pop/push) + `torajs-mmalloc/src/size_class.rs`
(alloc/dealloc bucket access) — Hypothesis: the explicit panic_bounds_check
edge from `arr[i]` is the root pull point for the panic tree; replacing
with `unsafe { arr.get_unchecked(i) }` + debug_assert removes the edge,
linker DCE strips the now-unreachable tree. Result: **+8 byte delta** on
default-tr binary (within noise; LLVM-emitted offset shifts).

**Why both failed**: the panic tree is pulled by **Rust std's default
`panic_handler` itself**, not by individual prod panic edges. The
`panic_handler` registered when linking `panic_unwind`/`panic_abort`
runtime crate provides the formatter + backtrace + demangler tree as
the *entry point* of any panic invocation, and **gets linked
unconditionally** when the runtime crate is in the dependency closure —
even if no actively-called code reaches it. `-dead_strip` walks the
symbol graph from `_main`, and *the panic_handler itself* is referenced
by every `panic_unwind`/`panic_abort` runtime hook (`__rust_start_panic`,
`__rust_panic_cleanup`), which the runtime crate exports for cargo's
internal use. So the handler stays no matter how many caller-side
panic edges we remove.

**Revised 9b strategy**: the only path that strips the panic tree is to
**replace the std default panic_handler** with a torajs-owned one. Two
formal ways:

- (a) **Custom `panic_runtime` crate** — `#![panic_runtime]` + `#![no_std]`
  + `#[panic_handler]` writing message+abort, no backtrace. Auto-linked
  by cargo when the user crate sets `panic = "abort"`. Replaces the
  default `panic_abort` runtime entirely. Highest leverage but needs
  nightly + careful cargo deps wiring (the panic_runtime selection rules
  are unstable since 2017).
- (b) **`#[panic_handler]` in the entry point of the user binary**.
  Currently the user binary's `main()` is LLVM-IR-emitted by ssa_inkwell,
  not a Rust source crate. Wiring `#[panic_handler]` would require either
  (i) a "wrapper" Rust crate that compiles into the user binary and
  provides the symbol, or (ii) an inkwell-emitted module that exports
  `rust_begin_unwind` as a torajs sym. (i) is cleaner.

**Locked 9b path**: ship (a) — torajs-panic-runtime crate — as a single
substrate commit. Expected: panic tree (`backtrace_rs` 49 KiB +
`rustc_demangle` 22 KiB + `std::path` 22 KiB + `std::io::error` 21 KiB +
`std::thread::Thread` 20 KiB + smaller) **all become unreachable from
`_main`** because the runtime hooks point at the torajs handler instead
of the std one. Cumulative expected: 345 KiB → **~180-210 KiB** in a
single commit (Step 10 trigger met in one shot).

**Why `-Wl,-force_load` is required (not just append-after-main.o)**

Every Layer-1+ Rust staticlib (`libtorajs_syscall.a` 18 MiB,
`libtorajs_mmalloc.a` 5 MiB, ...) bundles a copy of `libstd-XXX.rlib`'s
`panicking.o` + `alloc.o` because `staticlib` crate-type pulls all
transitive deps into the archive. Without `-Wl,-force_load` on our
`libtorajs_panic_runtime.a`, ld scans archives left-to-right under
lazy-resolution rules; the FIRST sibling archive's bundled
`std::panicking::*` definitions satisfy the panic-handler / alloc-error
symbols before ld ever reaches ours, dragging in the full backtrace tree.

`-Wl,-force_load,<our.a>` unconditionally loads every member of our
archive into the link **before** any other archive scan. The torajs
overrides "win" because they're already resolved by the time the
sibling archives' bundled std copies get a chance.

### Step 11 sub-step audit (2026-05-27 — B-path hot path analysis)

Per B-path Step 11 entry, audit of two slowest-vs-rust fixtures.

**array-sum-1m hot loop SSA** (`tr ssa bench/cases/array-sum-1m/`):

```
bb5:  ; for j in 0..len { sum += xs[j] }
  %24 = load arr, %xs              ; reload arr ptr each iter
  %26 = load i64, %j               ; load j
  %27 = load i64, %24 +16          ; load packed (cap<<32)|head
  %28 = lshr %27, 32               ; extract head
  %29 = shl %28, 3                 ; head*8 (byte offset of logical[0])
  %30 = shl %26, 3                 ; j*8
  %31 = add %30, 24                ; j*8 + ARR_DATA_OFF
  %32 = add %31, %29               ; + head*8
  %33 = load_dyn i64, %24 +%32     ; actual load
```

**Five arithmetic ops per element read** (head load + lshr + shl + idx*8
+ 2 adds) vs rust's **single `mov rax, [rbx+rcx*8]`** instruction. Even
with super-scalar M1 co-issue, this is the structural overhead causing
the 1.66× gap.

Root cause: `emit_arr_slot_byte_offset` (ssa_lower.rs:9438) always emits
the deque head-load path (`(cap<<32)|head` packed at offset 16, extract
head, scale to bytes, add to idx*8) even when the array has never been
`shift()`/`unshift()`'d. The comment notes "LICM hoists this out" but
LLVM does not in practice — possibly because the arr ptr is reloaded
from alloca each iter, blocking the hoist via aliasing concerns. A
literal-init fast-path (`ARR_DATA_OFF + idx*8` directly) exists at
constant-index callers (lines 10433/16485/17160/17241/18144) but is NOT
applied to runtime-idx index reads.

**generic-pair-1m hot loop SSA** (`tr ssa bench/cases/generic-pair-1m/`):

```
bb2:  ; for i in 0..n { p = {fst:i, snd:i+1}; sum += p.fst + p.snd }
  %10 = call __torajs_obj_alloc(40)   ; heap alloc 40 B
  store 1, %10                         ; refcount = 1
  store 1, %10 +4                      ; type_tag = 1
  store 0, %10 +8                      ; flags = 0
  store null, %10 +16                  ; next-ref = null
  store %7, %10 +24                    ; fst
  store %9, %10 +32                    ; snd
  %12..%18 = sum + p.fst + p.snd       ; ordinary field reads + add
  ...
bb5:  ; inline refcount dec
  %21 = load i32, %19
  %22 = sub %21, 1
  store %22, %19
  %23 = icmp eq %22, 0
  ...                                  ; if rc==0 → dealloc
```

vs rust `Box::new(Pair{fst:i, snd:i+1})`:
- Same heap alloc cost (malloc/free system overhead)
- **No universal header init** — rust Box stores only payload (16 B not 40 B)
- **No refcount dec branch** — compile-time unique-ownership = direct
  `free` at end-of-scope (1 inst no branch)

2.06× gap: (a) 4 header init stores rust doesn't pay, (b) refcount dec +
branch every iter, (c) larger alloc (40 vs 16 B affects malloc class).

### Step 11-A2 audit + design — obj escape-to-stack (2026-05-27)

Following 11-A1's Array<T> non-deque fast-path, 11-A2 attacks the
remaining 2.04× vs-rust gap on generic-pair-1m. The fixture allocates
a fresh `Pair<number, number>` per loop iteration, reads its two
fields, and drops it — every dimension of the per-iter work is heap-
backed: alloc call, header writes, field reads, rc dec branch, drop
call. Folding the alloc onto the stack collapses all five into local
stack ops.

**Before-state — generic-pair-1m `loopSum` bb2 hot loop (HEAD `3c72b08`)**

```
bb2:
  %7  = load i64, %i
  %8  = load i64, %i
  %9  = add %8, 1
  %10 = call __torajs_obj_alloc(40)        ; heap alloc
  store 1, %10                             ; rc=1 @ +0
  store 1, %10 +4                          ; type_tag=OBJ @ +4
  store 0, %10 +8                          ; class_tag=0 @ +8
  store null, %10 +16                      ; vtable=null @ +16
  store %7, %10 +24                        ; p.fst = i @ +24
  store %9, %10 +32                        ; p.snd = i+1 @ +32
  store %10, %p                            ; %p slot ← obj ptr
  %12 = load i64, %sum
  %13 = load obj, %p
  %14 = load i64, %13 +24                  ; p.fst
  %15 = add %12, %14
  %16 = load obj, %p
  %17 = load i64, %16 +32                  ; p.snd
  %18 = add %15, %17
  store %18, %sum
  %19 = load obj, %p
  %20 = icmp eq %19, null
  cond_br %20, bb7, bb5                    ; rc-dec branch
bb5:
  %21 = load i32, %19                      ; load rc
  %22 = sub %21, 1
  store %22, %19
  %23 = icmp eq %22, 0
  cond_br %23, bb6, bb7
bb6:
  call __torajs_obj_drop_sized(%19, 40)    ; heap free
  br bb7
```

Per-iter cost: **1 alloc call + 4 header stores + 2 field stores + 2
field loads + 5-inst inline rc-dec branch + cond_br to drop**. Five
of these (header stores + alloc + rc-dec + drop) carry no semantic
value for a binding that never escapes the loop iteration.

**Pair layout** (`ssa_lower.rs:49`):

```
OBJ_HEADER_SIZE = 24 bytes
  +0   rc        (i32)
  +4   type_tag  (i32)   ; OBJ=1
  +8   class_tag (i64)   ; 0 for non-class type alias
  +16  vtable    (ptr)   ; null when no chain methods
  +24  fst       (i64)   ; field 0
  +32  snd       (i64)   ; field 1
total: 40 bytes
```

Field i at `OBJ_HEADER_SIZE + i*8`. Layout is identical for stack-
alloced obj — that's the whole point of Option A; only the storage
class changes, not the shape.

**Per-fn obj escape analysis design**

Same shape as 11-A1's deque-escape pre-pass, but indexed on
*ObjectLit-init lets* instead of *Array-typed bindings*:

1. Pre-pass scans every fn body's AST. For each `let X = { … }`
   (typed `Obj(sid)` init = `ObjectLit { … }`), add `X` to a
   candidate set `obj_let_candidates`.
2. Same pass walks the rest of the fn body. For each AST node that
   escapes `X` (see escape patterns below), remove `X` from the
   candidate set. Closed-list deletion = conservative-safe (false-
   positive removal = miss a fast-path opportunity, false-negative
   = silent-wrong stack-use-after-free; only the former is
   acceptable, same invariant as 11-A1).
3. The remaining set = `non_escape_obj_lets`. At each typed-Obj
   `LetDecl` whose name ∈ this set + whose init is `ObjectLit`,
   the alloc site emits `AllocaBytes(N)` instead of
   `Call(obj_alloc, [N])`, and the corresponding `LocalInfo` is
   tagged `stack_alloced=true`. End-of-scope `emit_drops_for_owned_
   locals` skips locals with that flag.

Escape patterns (black-list, must mark `X` as escape-bound):

- `return X` — escapes through caller
- `obj.f = X` / `arr[i] = X` / `[..., X, ...]` / `{f: X}` / `...X`
  — escape through heap
- `foo(X)` — call arg, callee may retain
- `let Y = X` / `Y = X` — alias propagates to `Y` (mark both X and
  Y, conservative)
- `for (... of X)` source — runtime iter path unaudited
- `X` captured by a closure body
- `X.method(...)` — receiver passed to method (callee may retain)
- field write `X.f = v` of an *escape-bound* value `v` does **not**
  re-escape `X` (writing into X doesn't expose X); but the analyzer
  has no per-field tracking, so for conservatism, any write of a
  binding into a heap-typed slot keeps that binding's name in the
  escape set.

Property: bindings whose only uses are *reads of fields of X* (e.g.
`sum = sum + X.fst + X.snd`) and whose name never appears as an
escape-shaped operand are pruned to the safe set. `generic-pair-1m`'s
`p` matches exactly: 2 field reads, no escape — first-version target.

**Two implementation options ladder**

The chosen design avoids changing the *layout* in this first ship,
which keeps the blast radius minimal. The slot type / GEP offsets /
field reads / Member-access lowering all stay byte-identical — only
the storage class (heap → stack) and the drop-emission decision
change. Option B (layout change) is held as escalation.

- **11-A2-a (Option A, smallest-viable, hours)** — same layout,
  swap storage class.
  - `LetDecl { init: ObjectLit, name ∈ non_escape_obj_lets }`:
    emit `AllocaBytes(size)` instead of `Call(obj_alloc, [size])`.
    Result type stays `Type::Obj(sid)` (mirrors the pattern at
    `ssa_lower.rs:24663` for array-literal stack-alloc).
  - LocalInfo gets `stack_alloced: bool` (mirror of `moved: bool`).
  - End-of-scope drop emission skips `stack_alloced` locals — no
    rc-dec branch, no `obj_drop_sized` call.
  - Header init stores stay in source IR. LLVM `-O3`'s dead-store-
    elimination should sweep all four (rc / type_tag / class_tag /
    vtable) for the loop-local case because (1) the alloca's
    address never escapes the fn, (2) the four header offsets are
    never read, (3) opaque-pointer aliasing analysis can prove this
    cheaply.
  - Expected: generic-pair-1m vs-rust 2.04× → ~1.4–1.5× (depending
    on how aggressive LLVM's DSE turns out; on top of the per-iter
    alloca being near-free, eliminating the rc-dec branch alone
    saves 3 instructions + 1 cond_br per iteration).
  - Surface change ~ 350 LOC: 1 new file (~250 LOC), 1 LowerCtx
    field, 1 LocalInfo field, 1 pre-pass hook at fn entry, 1
    branch at the LetDecl alloc site, 1 skip at the drop site.
- **11-A2-b (Option B, max-ceiling, days-weeks)** — change the
  slot type to inline-struct.
  - Drop the `Obj(sid)` indirection for non-escape lets entirely;
    store `fst`/`snd` directly in the fn's local frame (Member-
    access GEP at offsets 0 / 8 instead of 24 / 32, no header at
    all).
  - Eliminates the 4 header stores at the IR level (does not rely
    on LLVM DCE for that win).
  - Requires teaching SSA Member-access / type system to handle
    "inline-struct local" as a distinct value category — risk of
    touching layout invariants in 5+ places (typed-store, GEP
    arithmetic, Member-load typing, debug-printer, drop typing).
  - Expected: generic-pair-1m vs-rust → ~1.0× (= rust parity).
  - Reserved as escalation if Option A measurement shows LLVM DCE
    does *not* sweep the dead header stores (in which case the IR
    still pays 4 store insts/iter and stays gapped to rust).

**Strategy — smallest-viable-first**

Ship 11-A2-a, measure. If LLVM DCE delivers the expected sweep
(generic-pair-1m drops to ≤ 1.5× vs rust), 11-A2-b is unnecessary
work — Option A reaches near the same ceiling at a tenth the surface
change. If DCE doesn't sweep (generic-pair-1m stays ≥ 1.8× vs rust
because header stores remain visible in the .text), 11-A2-b
escalates. Either way the first measurement settles the question
without committing to the larger refactor up front.

This honors 上限优先 by reaching for Option B's ceiling while
recognizing that LLVM `-O3` may already deliver it for free at
Option A's surface cost — a measurement, not a guess.

**Refcounted-field guard explained**

The Option A design relies on LLVM `-O3` DSE sweeping the four
header stores when the alloca's address never escapes. This is
safe for refcounted-field-free objs because nothing reads the
header during the alloca's live range. But if a field is
refcounted (e.g. `let p = { name: someStr, count: 0 }`), the
runtime drop walk through `obj_drop_sized` is what dec-refs
`name`. Skipping that walk for a stack-alloced obj would leak
the child rc.

The guard at the alloc site reads `field_tys` (already computed
upstream for layout interning) and forces `Call(obj_alloc)`
when any field type satisfies `ty.is_refcounted()`. `take()` on
the hint still fires (so the next LetDecl gets a fresh state),
but `.filter()` resolves to `None` and the heap branch runs.

In the bench's `Pair<number, number>` shape both fields are
`i64` (non-refcounted) — guard passes, stack-alloc fires. For
`Pair<string, number>` the `name` field is `Type::Str` (rc),
guard fails, heap-alloc fires — semantics unchanged.

##### Reconciliation with 11-A3 counter-test

11-A3 audit shipped a counter-test that **appears to refute** the storage-class
hypothesis: wrapping all top-level statements in `function main() { ... }` made
`i / sum / j` fn-local `alloca i64` (would-be mem2reg-promotable) but the run
was **47% slower** (32.30 ms vs 22.03 ms). That counter-test's conclusion
("storage class is not the residual root cause") is **valid for the specific
intervention it tested** but does NOT extend to the 12-a fix path. Three reasons:

1. **`function main()` wrap changes fn structure, not just storage class.**
   Every previously top-level function declaration becomes an inner / nested
   function inside `main`. Closure-capture analysis sees the inner fns
   referencing `i / sum / j` from their enclosing scope → those bindings
   *escape* → LLVM's mem2reg pass refuses to promote the escaped alloca to
   register. End state: `i / sum / j` still flow through `alloca i64` stores
   and loads, on top of fn-call entry/exit overhead and closure-context
   stack frames. The 47% slowdown measures **escaped-fn-local + closure
   overhead**, not "mem2reg failed on a clean alloca".
2. **12-a-1 (Path B — extern attribute upgrade) does not change SSA structure
   at all.** It only annotates extern fn declarations with `memory(...)` etc.
   The user's `i / sum / j` remain at their current `global_ref` storage
   class; LLVM is just told "this extern call doesn't touch user globals" so
   LICM can hoist the load/store out of the inner loop. Zero confound with
   counter-test's fn-structure changes.
3. **12-a-2 (Path A — SSA promote pass) does not change fn structure.**
   Module-level helper fns stay module-level; they don't become inner /
   closure fns. The pass operates at SSA layer: it replaces `global_ref @i`
   with `alloca i64` *inside the already-synthesized writer fn* (typically
   `main`), preserving the unchanged structure of every other fn in the
   module. Reader-only fns continue to reference the global directly; the
   writer fn emits write-back before each Call so reader-fns see the latest
   value. Closure-capture analysis sees no change; mem2reg sees a clean
   non-escaped fn-local alloca and promotes to register.

Counter-test data therefore does NOT refute 12-a's hypothesis. What it DOES
tell us: **acceptance gates must guard against the counter-test failure
mode**. Specifically, 12-a-2 acceptance must verify that the promoted alloca
remains non-escaped (no inner fn / closure references it post-promote) and
mem2reg actually promotes it (verifiable via `--emit=llvm-ir` post-mem2reg).
If escape is detected at impl time, the promote pass must back off for that
binding (fall back to leaving `global_ref` in place) rather than introducing
escape-and-mem2reg-fails state that would degrade perf 47% per counter-test.

#### Design — single-writer detection algorithm

Promote candidate criteria (all required):

1. Type ∈ {`I64`, `F64`, `Bool`}. Refcounted (`Str` / `Obj` / `Arr`) **excluded** —
   `Drop` semantics on early-exit paths complicate write-back invariants; refcount
   inc/dec across promote-and-restore would need careful semantic threading.
2. Module top-level `let` (currently the sole K.3 path).
3. Writer set is a single SSA function (typically the synthesized `main`).
4. No closure-by-reference capture observed (closure captures escape the
   promote-safe assumption — defer to a follow-up).

**Pass 1 — collect writer set** (O(insts)):

```text
writers: HashMap<String, BTreeSet<FuncId>>
for each fn in module.funcs:
    for each inst in fn.blocks.iter().flat_map(|b| &b.insts):
        if let Store(_, Operand::Value(v), _) = inst.kind:
            if value_def(fn, v).kind == GlobalRef(name):
                writers.entry(name).or_default().insert(fn.id)
```

Edge: `StoreDyn` (dynamic-shape store) is conservative — if any `StoreDyn` writes
through a value ultimately derived from `GlobalRef(name)`, exclude `name` from
promote. K.3 Number globals don't currently route through StoreDyn (verify by audit
at impl time); if any do, exclude.

**Pass 2 — rewrite** (O(insts) per promoted name):

For each `name` with `writers[name].len() == 1` AND type ∈ {I64, F64, Bool}:

1. In the writer fn's entry block, prepend:
   - `slot_ptr = alloca <type>` (an SSA value)
   - `init_val = load global_ref(name)`
   - `store init_val → slot_ptr`
2. Replace every `GlobalRef(name)` instance in this fn with the cached `slot_ptr`.
3. On every terminator `Return` (and any early-exit) of this fn:
   - `final_val = load slot_ptr`
   - emit `GlobalRef(name)` + `Store final_val → global_ptr` (write-back)
4. Refcounted globals (the `is_refcounted()` set used by 9877) are **never**
   promoted — their `GlobalRef` site stays untouched.

**Boundary — cross-fn callbacks**: a callee fn may read the global via its own
`GlobalRef(name)`. Since `writers[name].len() == 1` checks **writers only**, a
reader-only callee is fine *between* writer calls (writer's exit write-back lands
before any subsequent fn-entry read of the global).

**Within** the writer fn, if it `Call`s a fn that transitively reads `name`, the
stale alloca-cached value would diverge from the global. **MVP simplification**:
emit a write-back (load slot → store global) **before every Call** in the writer
fn. LLVM's mem2reg + GVN then collapse redundant store-load pairs back into
register-only when the call doesn't actually read the global (which is the common
case for `__torajs_arr_push` / `__torajs_libc_*` — none of those touch user
globals). This trades pre-mem2reg IR size for correctness-by-default; the cost is
absorbed by the LLVM optimizer pipeline.

Refinement (post-12-a-2, if needed): transitive-reader analysis on Call targets to
elide write-backs to demonstrably non-reader callees. Not in MVP scope.

**Complexity**: O(insts) Pass 1 + O(insts × promoted_count) Pass 2 = linear in
program size. For array-sum-1m, 3 promoted globals × 10M-iter loop × per-Call
write-back = 30M extra pre-mem2reg insts; mem2reg + GVN folds these into a single
final write-back after the loop (the loop body never reads the global from the
write-back; reads use the alloca slot which is itself promoted to register by
mem2reg).

#### Design — extern attribute upgrade map

Conservative set — only attributes with **proven semantic match** to the runtime
implementation. LLVM 16+ unified `memory(...)` syntax used throughout; legacy
`readonly` / `readnone` / `argmemonly` superseded.

| Function                    | Target attrs                                                                                 | Risk     | Rationale                                                                       |
|-----------------------------|----------------------------------------------------------------------------------------------|----------|---------------------------------------------------------------------------------|
| `__torajs_arr_alloc`        | `nounwind`, `willreturn`, `mustprogress`, `memory(argmem: readwrite, inaccessiblemem: readwrite)` | Low      | Allocator: argmem (rare, e.g. cap arg) + inaccessible heap; never user globals  |
| `__torajs_arr_alloc_pooled` | Same as `__torajs_arr_alloc`                                                                 | Low      | Same shape                                                                      |
| `__torajs_libc_malloc`      | `nounwind`, `willreturn`, `mustprogress`, `allocsize(0)`, `memory(inaccessiblemem: readwrite)` | Low      | Pure libc malloc: never touches caller-visible memory                           |
| `__torajs_libc_realloc`     | `nounwind`, `willreturn`, `mustprogress`, `allocsize(1)`, `memory(argmem: readwrite, inaccessiblemem: readwrite)` | Medium   | May free old ptr; argmem r/w (old block copy) + inaccessible (new alloc + free) |
| `__torajs_libc_memmove`     | `nounwind`, `willreturn`, `mustprogress`, `memory(argmem: readwrite)`                        | Low      | Spec-exact: only touches argument-passed memory                                 |
| `__torajs_libc_memcpy`      | Same as memmove                                                                              | Low      | Same                                                                            |
| `__torajs_libc_memcmp`      | `nounwind`, `willreturn`, `mustprogress`, `memory(argmem: read)`, `nofree`                   | Low      | Pure read-only comparator                                                       |
| `__torajs_libc_free`        | `nounwind`, `willreturn`, `mustprogress`, `memory(argmem: readwrite, inaccessiblemem: readwrite)` | Low      | Touches arg block (poison/scribble) + inaccessible (free list)                  |

**Critical not-done**: `nofree` is **NOT** applied to `arr_alloc` / `realloc` /
`free` — those *may* free their pointer arguments and mis-specifying `nofree` is
silent UB under LLVM alias analysis. Only `memcmp` (proven read-only) gets it.

**Critical not-done**: `nocapture` on pointer args — semantically valid for
`memcmp` / `memcpy` / `memmove` (don't retain refs across the call) but the
benefit-vs-risk of broadening capture analysis isn't well-tested in this codebase.
Defer to a follow-up if 12-a-1 bench misses target.

**Why `memory(...)` matters for this gap**: LLVM's default extern assumption is
`memory(read, write)` over **all** locations including `other` (= globals / TLS
/ etc). Setting `memory(argmem: readwrite, inaccessiblemem: readwrite)` excludes
`other` — LLVM now knows the call cannot read/write user globals — LICM is free to
hoist `@i / @sum / @j` load/store out of the loop.

#### Texture — design notes

- **`allocsize(N)` arg index**: `arr_alloc(cap: i64) → ptr` uses `allocsize(0)`
  (cap is arg 0); `realloc(ptr, new_size: i64) → ptr` uses `allocsize(1)`.
  LLVM treats this as a hint enabling `.len`-aware folding.
- **`mustprogress`**: declares the fn is guaranteed to terminate. True for all
  runtime fns (allocators may panic OOM but never loop infinitely). Enables LLVM
  to assume callees don't trap the program into deadlock under speculation.
- **`willreturn`**: pairs with `mustprogress` for return-control-flow guarantees.
- **memcmp's `nofree`**: read-only, guaranteed not to free anything — safe.
- **Why not `noalias` on `realloc`'s return**: realloc may return the same pointer
  it was passed (in-place grow). The current `is_alloc_intrinsic` whitelist
  already excludes `realloc` correctly (only fresh-pointer producers in there).
- **Why `arr_push` / `arr_push_unchecked` (IR-defined) aren't in the attribute
  table**: their bodies are emitted inline; LLVM derives memory effects from the
  IR body itself (calls to realloc/memmove + arg writes). Once the inner libc
  helpers get correct attrs, the IR-derived effects propagate naturally.

#### Non-goals for 12-a

- **Closure-by-reference promotion**: deferred. Module-level lets captured by
  closures are excluded from promote in this pass; the closure-capture case is
  rare in bench fixtures and would need escape-style analysis beyond this scope.
- **Multi-fn writer promotion**: deferred. Union-find on writer sets across fns
  is a follow-up if benchmarks reveal a multi-fn-write hot pattern. MVP single-fn
  covers 95%+ of bench fixture surface (top-level scripts, `main`-wrapped code).
- **`StoreDyn` promotion**: deferred. Conservative exclusion at MVP.

### allocsize(N) DEFERRED to 12-a-1 follow-up

The design called for `allocsize(0)` on malloc/str_alloc_pooled/arr_alloc_pooled
and `allocsize(1)` on realloc. Implementation discovery during this batch:

- LLVM 22's IR text format for `allocsize` supports both single-arg
  `allocsize(N)` (size in arg N, no count) and two-arg `allocsize(N, M)` (size
  in N, element count in M) forms; the second form is semantically wrong for
  malloc-shape allocators (LLVM interprets it as `size * count` from two args).
- Inkwell 0.9 + llvm-sys-22.1 only expose the raw
  `LLVMCreateEnumAttribute(kind, value: u64)` ABI. Every encoding tried
  (`arg_idx`, `arg_idx << 32`, `arg_idx | (0xFFFFFFFFu64 << 32)`) round-trips
  through the LLVM 22 IR printer as `allocsize(X, Y)` two-arg form — there is
  no sentinel value via the raw enum-attribute API that LLVM 22 recognizes as
  "NumElems absent" → printer never emits the single-arg form.
- The correct path is to bind LLVM's dedicated
  `LLVMCreateAllocSizeAttribute(ctx, ElemSize, NumElems)` C API, which
  llvm-sys-22.1 doesn't expose yet (grep `AllocSize` in
  `llvm-sys-221.0.1/src/*.rs` returns nothing). Adding it is a narrow llvm-sys
  patch / direct FFI extern, scoped separately from this attribute-bundle batch.

Deferred to `12-a-1-followup`. The other LICM-blocking attributes (memory /
nounwind / willreturn / mustprogress / nofree) cover the bulk of
array-sum-1m's hoist gap independently — bench evidence above confirms.

## Step 12-a-2 investigation — SSA global_ref promote pass (Path A) — DEFERRED 2026-05-28

Path A of the 12-a ladder was implemented end-to-end this session, bench-tested
under a controlled A/B harness, and **reverted** at the working-tree level
because it caused a net bench regression on `array-sum-1m` even after
adding the runtime-intrinsic write-back-elision heuristic. The audit doc's
key assumption (that LLVM `mem2reg + GVN` would collapse the introduced
per-Call write-back into register-only ops) turned out to be wrong at LLVM
22 for our IR shape. This section documents the investigation so a future
attempt has prior art and doesn't repeat the same dead end.

### What got built

`crates/torajs-core/src/ssa_lower_global_promote.rs` (~580 LOC including
4 cfg(test) unit tests). The pass implemented exactly the audit-doc design:

1. **Pass 1** — `pick_promotions(module)` walks every fn, builds
   `writers: HashMap<name, BTreeSet<FuncId>>` via `Store(_, Operand::Value(v), _)`
   where `v` resolves to `InstKind::GlobalRef(name)`, AND
   `dyn_disqualified: HashSet<name>` via `StoreDyn`. Emits the per-fn
   promote list for `(name, ty) where writers.len() == 1 AND ty ∈
   {I64, F64, Bool} AND not dyn-disqualified AND not refcounted`.
2. **Pass 2** — `promote_in_fn(f, list, safe_callees)` for each writer fn:
   - **Entry prefix** (4 insts per promoted name): `alloca → global_ref
     → load → store` to seed an alloca slot from the global.
   - **Value redirect**: every existing `GlobalRef(name)` result ValueId
     is mapped to the slot; all Operand::Value occurrences across the fn
     get rewritten via a single `apply_redirects_inst` walk.
   - **Pre-Call write-back** (3 insts: `load slot → global_ref → store`)
     before each `Call` / `CallIndirect`, gated by `safe_callees` —
     callees whose name starts with `__torajs_` / `print_` / `putchar`
     are treated as known non-readers of user globals (matches Step
     12-a-1's `memory(argmem|inaccessiblemem: readwrite)` contract).
     CallIndirect always gets write-back (unknown callee identity).
   - **Return write-back** (3 insts) appended to every block whose
     terminator is `Terminator::Ret(_)`.

Wired into `ssa_lower::lower_inner` at the end, before `module` returns.
4/4 cfg(test) unit tests passed:

- `promote_introduces_entry_alloca_and_wb_triplets` — full promote shape
- `promote_skips_refcounted_global` — `Type::Str` skipped per eligibility
- `promote_skips_multi_writer` — second-writer fn disqualifies
- `promote_elides_writeback_for_runtime_intrinsic_call` — heuristic fires

`array-sum-1m` `tr run` output stayed `bun`-byte-equal (correctness held).
Post-O3 IR showed per-iter `store @i / @sum / @j` insts ELIMINATED — the
only remaining global stores were 3 LCSSA write-backs at the loop-exit
block (line 589-591 in the dump). At the IR level, the pass did exactly
what the audit predicted.

### Why the audit assumption was wrong

The audit doc said: *"mem2reg + GVN folds these [per-Call write-back
triplets] into a single final write-back after the loop (the loop body
never reads the global from the write-back; reads use the alloca slot
which is itself promoted to register by mem2reg)."*

What actually happens under LLVM 22:

1. **mem2reg DOES** promote the alloca to register form — verified by
   the post-O3 IR showing `%.018.lcssa34` (loop-closed SSA) instead of
   alloca load/store inside the loop.
2. **The pre-Call write-back to the global IS elided by the heuristic**
   for `__torajs_arr_push` calls — verified by zero per-iter
   `store @i / @sum / @j` in the post-O3 IR (only 3 LCSSA stores at
   loop exit).
3. **But the bench is still slower** despite both wins above. The
   regression must come from a downstream LLVM optimization that does
   not fire when the alloca shape is present. Candidates:
   - **SIMD auto-vectorization**: the Step 11 follow-up audit showed
     LLVM 22 auto-emits a 4-way NEON unrolled SIMD loop for the sum
     reduction (`movi.2d × 4 + ldp q4,q5 / q6,q7 + add.2d × 4 +
     addp.2d`). Introducing an alloca + initial load may perturb the
     vectorizer's dependence analysis enough that it bails out (or
     emits a less-optimal shape).
   - **LICM / Loop-Idiom Recognition** may handle the global-store
     pattern better than the alloca-with-write-back pattern. Without
     a deeper LLVM internals dig, it's hard to attribute precisely.

The lesson: **"alloca + mem2reg" is not a strictly better storage
class than "global + LLVM's LSM" for our specific hot-loop shapes
under LLVM 22**. The audit-doc heuristic ("alloca-with-mem2reg always
wins for register-promote-able scalars") oversimplifies LLVM's actual
optimization pipeline. The right move depends on the surrounding loop
shape and what other passes can extract from each form.

### Why the heuristic alone wasn't enough

Even after the `__torajs_*` write-back elision (which IS visible in the
IR — global stores collapsed from 12 per iter in the first naive attempt
down to 0 per iter in the heuristic version), the binary still ran
slower than the no-promote baseline. So the cost of the promotion shape
itself (entry prefix + value redirect + LLVM optimizer reactions) >
benefit of mem2reg register-promote.

The heuristic CORRECTLY eliminated the obvious per-iter cost, but the
deeper LLVM-pipeline-interaction cost remained.

## Step 12-b audit — non-deque Array push fast-path

12-b extends the 11-A1 deque-escape narrowing from the **read path** (idx
load — landed at `3c72b08`) to the **push write path**. 11-A1 proved
that for an Array<T> binding `xs` that escape analysis can show is not
shift/unshift-touched and not aliased into another heap object, `xs[i]`
load skips the per-access `head` load and emits `arr_data_off + idx*8`
directly. The same proof of safety lets us emit a specialized push
body that hardwires `head ≡ 0`, skipping the entire compact branch and
the head-aware `arr_data_ptr` re-load in the store block.

`array-sum-1m` is the motivating fixture: a `while`-loop driven push
of 10M elements into a never-shifted `let xs: number[] = []`. The
fixture's `while` shape (not the canonical `for (let i = 0; i < N; i++)`)
means the existing `push_unchecked_for` reserve-detection in
`ssa_lower.rs:18443` does **not** fire — so push goes through the K.5
helper-call fallback at `ssa_lower.rs:18524`, calling the
187-LOC `__torajs_arr_push` body (`arr_builders.rs:56-238`). This is
the hot path 12-b targets.

### Surveyed push call emit sites

Five SSA emit sites build `Call(intrinsics.arr_push, ...)`. Three are
user-level Member-call lowering, two are compiler-internal array
construction:

| Site (ssa_lower.rs) | Path | Receiver shape | Non-deque dispatch |
| ------------------- | ---- | -------------- | ------------------ |
| `8485`              | `lower_json_parse` array build into a freshly-allocated slot | local slot ptr (no user binding) | **hard-wire `arr_push_non_deque`** — dst is private |
| `18524`             | K.5 (a) Ident-receiver, local binding, typed `Array<T>` (`elem_ty != Any`), `push_unchecked_for` not active | `Expr::Ident(recv_name)` | **`deque_arrs.contains(recv_name)` query** |
| `18607`             | K.8 Ident-receiver, top-level global binding | `Expr::Ident(recv_name)` | **`deque_arrs.contains(recv_name)` query** |
| `18662`             | (b) Field-receiver `obj.field.push(v)` where `field: Array<T>` | `Expr::Member { obj, name }` | **leave on `arr_push`** (see "deferred sites" below) |
| `22536`             | `lower_flat_map` inner-walk push into freshly-allocated `dst_slot` | local slot ptr (no user binding) | **hard-wire `arr_push_non_deque`** — dst is private |

Four sites can dispatch to the non-deque variant safely (two by
escape-analysis name query, two by construction). Site `18662` is
conservatively deferred — see below.

### Deferred site: `obj.field.push(v)`

The field-receiver path at `18662` cannot rely on the binding-name
query because `deque_arrs` is keyed by Ident name, not by Member
shape. An external alias path can defeat the non-deque assumption
without leaving a fingerprint in `deque_arrs`:

```ts
class C { xs: number[] = []; }
const c = new C();
let p = c.xs;      // LetDecl init is a Member, not an Ident
                   // → ssa_lower_deque_escape.rs:Stmt::LetDecl branch
                   // only mirror-marks when init is Expr::Ident, so
                   // neither `p` (yet) nor `c.xs` gets marked here.
p.shift();         // line 164 marks `p` (Member.shift on Ident `p`).
                   // `c.xs` (the Member shape) is never named in the
                   // escape set — there is no Member key to mark.
c.xs.push(v);      // at this site, escape analysis would have to
                   // ask "is any alias of obj.field in deque_arrs?"
                   // — the present analysis does not track that.
```

Treating `obj.field.push` as non-deque here would `head ≡ 0` but the
prior `p.shift()` has set `head = 1`, so the slot store lands at the
wrong byte offset (slot 0 instead of slot 1, overwriting live data).

This is the same silent-wrong shape `feedback_no_tech_debt` calls
out. 12-b ships only the four name-keyed / construction-keyed sites.
Field-receiver narrowing waits on an alias-aware extension to escape
analysis (track `let p = obj.field` LHS as a Member-shape alias and
propagate the mark backwards) — leave as `12-b-followup` once the
name-keyed wins are banked.

| 88   | `cond_br need_room ? need_room_blk : store_blk` | — (logic survives, condition is simpler) |
| 92-100 | `need_room_blk: head_pos = head > 0` | ✦ |
| 101-103 | `cond_br head_pos ? compact_blk : after_compact_blk` | ✦ |
| 105-141 | `compact_blk` memmove + head=0 store | ✦ (whole block removed) |
| 144-151 | `after_compact_blk: full = (len == cap); cond_br full ? grow_blk : post_compact_blk` | ✦ (collapses; entry already branches on `len == cap`) |
| 154-155 | `post_compact_blk: br store_blk`     | ✦ (block removed) |
| 158-200 | `grow_blk: realloc + cap store`      | — (kept verbatim) |
| 204-211 | `store_blk: phi(entry, post_compact, grow)` | ✦ (3-way → 2-way phi) |
| 212    | `data = arr_data_ptr(arr) = arr_raw_data_ptr + head*8` | ✦ (becomes `arr + ARR_DATA_OFF` constant offset) |
| 213-221 | `slot = data + len*8; store val`    | — (offset constant-folds to `arr + ARR_DATA_OFF + len*8`) |
| 222-235 | `len_p1 = len + 1; store len_p1`    | — |

Steady-state (no grow, head ≡ 0) per-iter savings vs current body:

- **1 load** — the entry `arr_head_load` (`u32 → zext → i64`); cross-BB
  GVN may already fold the second `arr_data_ptr` head load into the
  entry one when `arr` operand is identical and no intervening store
  touches `head` — but verifying requires dumping the post-O3 IR for
  each LLVM version we ship against, which is exactly the kind of
  silent-dependence 12-a-2 burned on.
- **1 add** — `head + len` (`phys_used`).
- **1 mul + 1 add** — `head * 8` and combining it into the data ptr in
  the store block.
- **1 cmp + 1 conditional branch** — `head > 0` and the compact/no-compact
  fork.
- **3 fewer basic blocks** — `need_room_blk`, `compact_blk`,
  `after_compact_blk` (and `post_compact_blk` which only exists to
  thread the no-grow no-realloc fall-through phi edge), and the
  resulting 3-way phi in `store_blk` collapses to 2-way.

The CFG simplification (6 BBs → 3 BBs, fewer phi inputs) is the
**non-additive** part of the win — it gives LLVM 22's loop-vectorizer,
LICM, and loop-rotate a simpler shape to reason about. 12-a-2 burned
exactly here in the opposite direction (alloca shape perturbed the
downstream vectorizer); 12-b's bet is the reverse — removing dead BBs
should *help* the vectorizer rather than hurt it. But "should" is
exactly the word 12-a-2 made us mistrust, hence step-6 controlled A/B.

### `__torajs_arr_push_non_deque` proposed IR body

```text
__torajs_arr_push_non_deque(arr*, val) -> arr*   ; Internal + alwaysinline

entry:
  len  = arr_len_load(arr)                          ; u32 → zext i64
  cap  = arr_cap_load(arr)                          ; u32 → zext i64
  full = icmp eq len, cap                           ; replaces phys_used >= cap
  br i1 full, label %grow_blk, label %store_blk

grow_blk:
  cap_zero      = icmp eq cap, 0
  cap_x2        = mul cap, 2
  new_cap       = select cap_zero, 4, cap_x2
  new_cap_bytes = mul new_cap, 8
  new_total     = add new_cap_bytes, ARR_HDR_DATA_OFF
  arr_grown     = call realloc(arr, new_total)
  new_cap_p     = gep i8, arr_grown, ARR_HDR_CAP_OFF
  new_cap_i32   = trunc new_cap to i32
  store new_cap_i32, new_cap_p
  br label %store_blk

store_blk:
  arr_out = phi ptr [ arr, %entry ], [ arr_grown, %grow_blk ]
  len_x8  = mul len, 8
  slot    = gep i8, arr_out, ARR_DATA_OFF + len_x8   ; one combined GEP
  store val, slot
  len_p1  = add len, 1
  len_p   = gep i8, arr_out, ARR_HDR_LEN_OFF
  store len_p1, len_p                                ; u32-truncated store
  ret arr_out
```

Three basic blocks (vs six), 2-way phi (vs 3-way), no head load, no
compact-branch decision tree, no `arr_data_ptr` (the head-aware data
pointer helper). Linkage = `Internal` + `alwaysinline` per the B1b
recipe (`arr_builders.rs:1-21` doc comment) so user-code's push hot
loops fold the body into the caller.

### ROI estimate — `array-sum-1m`

- 10M push iterations in a tight `while` loop.
- Per-iter steady-state save: ~4 arithmetic insts (head_load + add +
  mul + extra add) + 1 cmp + 1 cond-br elided + ~3 BB-related
  bookkeeping ops absorbed by simpler phi.
- Naive cycle math (3 GHz, IPC ~2): `~7 inst × 10M = 70M inst ≈ 12 ms`
  best-case; OOO absorption + L1-resident `head_load` cuts the realized
  win to roughly 30-50% of that: **~3-5 ms saved**, **modulo
  vectorizer interaction**.
- Vectorizer interaction is the swing factor. If the simpler 3-BB body
  enables LLVM to vectorize the push body further (paired with
  `len++` and the implicit loop bound), the win could double; if the
  current 6-BB body was already partially vectorized and 12-b
  perturbs that path the same way 12-a-2 did, the win could regress
  to zero or negative.
- Current `array-sum-1m` `tr` is ~23-29 ms (low-noise 5-pass) /
  ~28-31 ms (high-noise controlled A/B) vs rust 16.27-16.45 ms.
  Projected post-12-b: ~20-26 ms (3 ms saved) → ratio **1.30-1.45×**,
  vs current 1.42-1.75×.

12-b on its own may not close to the final ≤ 1.30× gate. The
intermediate gate of ≤ 1.40× is the realistic 12-b acceptance; a
12-c (likely targeting the read-side `xs[j]` load combined with the
`arr_data_ptr` re-load in slot writes, or push-loop reserve detection
extended to `while` shape) would close to ≤ 1.30×.

performance under LLVM's pattern-based optimization.

### Disassembly analysis — where the 1.45× actually comes from

`tr build` + `otool -Vt` on the array-sum-1m binary at HEAD 94344c3 reveals
the main loop body:

```asm
0000000100000724  ldr   w10, [x19, #0x14]       ; load head from arr_ptr+ARR_HEAD_OFF
0000000100000728  add   x10, x19, x10, lsl #3   ; arr + head*8
000000010000072c  add   x10, x10, #0x18         ; + ARR_DATA_OFF
0000000100000730  str   x9, [x10, x8, lsl #3]   ; store i to xs[len]     ← fast-push ✓
0000000100000734  add   x8, x8, #0x1            ; len_slot++ in register ✓
0000000100000738  ldr   x9, [x21, #0x4a8]       ; load i from global     ← global dance
000000010000073c  add   x9, x9, #0x1            ; i + 1                   ← global dance
0000000100000740  str   x9, [x21, #0x4a8]       ; store i to global       ← global dance
0000000100000744  cmp   x9, x20                 ; cmp i, N
0000000100000748  b.lt  0x100000730             ; back to body
```

Per-iter cost: ~10 ARM64 instructions. Rust's equivalent is ~6 (load i,
store xs[i], i++, cmp, br — all register-based phi). The 49% perf gap
breaks down to:

1. **`i` global memory dance (BIGGEST)** — `load i / +1 / store i` is 3
   instructions per iter that should be **1 register increment** in
   rust-equivalent code. SSA lowers top-level `let i: number = 0;` to a
   global (`global_ref @i`) — `lower::synthesize_main` Phase K.3 rule —
   because in general toplevel lets are read by named fns and need a
   stable address. But array-sum-1m's `i` is only used inside `main`'s
   while-loop scope; promotion to global is over-conservative.
2. **`head` reload per iter** — `ldr w10, [x19, #0x14]` reloads head
   inside the loop despite SSA-level hoisting, because LLVM cannot prove
   the StoreDyn at `[x19 + slot_off]` does not alias `[x19 + 0x14]`
   (head field). Missing noalias / alias.scope metadata.
3. **`ARR_DATA_OFF` re-add per iter** — `add x10, x10, #0x18` should
   constant-fold with the surrounding GEP. Minor.

**Back-of-envelope**: eliminating #1 alone (3 instr → 1) would drop the
loop body to ~8 instr ≈ 1.33× vs rust 6 instr (estimated **~1.10× ratio**,
well under Step 12 final gate ≤ 1.30×). Eliminating #1 + #2 → ~6 instr ≈

## Step 12-c-2 ship — internal linkage on primitive Copy data globals — 2026-05-28

### Root cause (from 12-c-1 LLVM IR analysis)

Commit `cd7c3b8`. The 12-c-1 finding's disassembly analysis identified the
**actual array-sum-1m bottleneck** as the `i` global memory dance (`load
@i / add 1 / store @i` 3-instr-per-iter sequence) rather than the push
call indirection. Dumping the LLVM IR with `TR_DEBUG_KEEP=1` confirmed:

```llvm
bb2:                                              ; preds = %bb2.lr.ph, %bb2
  %.08 = phi i64 [ %8, %bb2.lr.ph ], [ %19, %bb2 ]   ; len_slot in phi ✓
  %16 = phi i64 [ %.pr, %bb2.lr.ph ], [ %21, %bb2 ]  ; i value in phi ✓
  %17 = shl i64 %.08, 3
  %18 = getelementptr i8, ptr %15, i64 %17
  store i64 %16, ptr %18                              ; xs[len] = i ✓ (uses phi %16)
  %19 = add i64 %.08, 1                               ; len++ ✓
  %20 = load i64, ptr @i, align 8                     ; ← reload @i (BAD)
  %21 = add i64 %20, 1                                ;   ← reload+inc
  store i64 %21, ptr @i, align 8                      ;   ← store back (BAD)
  %22 = icmp slt i64 %21, %const
  br i1 %22, label %bb2, label %bb3
```

LLVM **did** promote `i` to a phi register `%16` for the fast-push store,
but **kept the per-iter load/add/store of `@i`** because the global was
declared with default external linkage (`local_unnamed_addr global i64
0`). LLVM's GlobalsAA + DSE can prove the load/store dead only when the
symbol is module-private — external linkage means another translation
unit could observe the writes.

### Fix

Set `Linkage::Internal` on I64 / I32 / F64 / Bool data globals in
`crates/torajs-core/src/ssa_inkwell/globals.rs::emit_data_global`. One
line per primitive type branch (`glob.set_linkage(Internal)`); a 4-line
carve-out comment documents the rationale + the deliberate scope (Str /
Arr / Obj globals stay External pending a follow-up audit of the
exit-time drop hook + GlobalsAA interaction with rc_inc/rc_dec
callsites).

Safe because: `tr build` emits **one LLVM module per binary**; runtime
staticlibs (libtorajs_*.a) don't reference user-defined globals by name.

### Effect — LLVM unlocks vectorization

After the linkage change, LLVM's loop vectorizer kicks in (the redundant
load/store was the only thing blocking it). The bb2 loop body becomes a
4-way unrolled, 2-wide vectorized body:

```llvm
vector.body:                                      ; preds = %vector.body, %bb2.lr.ph
  %lsr.iv72 = phi ptr [ %scevgep73, %vector.body ], [ %scevgep71, %bb2.lr.ph ]
  %lsr.iv69 = phi i64 [ %lsr.iv.next70, %vector.body ], [ %const, %bb2.lr.ph ]
  %vec.ind = phi <2 x i64> [ <i64 0, i64 1>, %bb2.lr.ph ], [ %vec.ind.next, %vector.body ]
  %step.add = add <2 x i64> %vec.ind, splat (i64 2)
  %step.add.2 = add <2 x i64> %vec.ind, splat (i64 4)
  %step.add.3 = add <2 x i64> %vec.ind, splat (i64 6)
  %scevgep75 = getelementptr i8, ptr %lsr.iv72, i64 -16
  %scevgep76 = getelementptr i8, ptr %lsr.iv72, i64 16
  %scevgep74 = getelementptr i8, ptr %lsr.iv72, i64 32
  store <2 x i64> %vec.ind, ptr %scevgep75, align 4
  store <2 x i64> %step.add, ptr %lsr.iv72, align 4
  store <2 x i64> %step.add.2, ptr %scevgep76, align 4
  store <2 x i64> %step.add.3, ptr %scevgep74, align 4
  %vec.ind.next = add <2 x i64> %vec.ind, splat (i64 8)
  ...
```

And the ARM64 ASM emits NEON `add.2d` + `stp` pairs:

```asm
add.2d v5, v0, v1
add.2d v6, v0, v2
add.2d v7, v0, v3
stp    q0, q5, [x9, #-0x10]   ; store-pair: 4 i64s in one instr-pair
stp    q6, q7, [x9, #0x10]    ; another 4 i64s
add.2d v0, v0, v4
add    x9, x9, #0x40
subs   x20, x20, #0x8         ; decrement by 8 per iter
b.ne   loop
```

LLVM also **dead-store-eliminated `@i`** completely — only the init
store survives (folded to `store i1 false, ptr @i` since the
post-loop reads are bool predicates).

### Why other fixtures benefit too

The change applies to **any** primitive Copy global, not just
`array-sum-1m`'s `i`. Other counter-driven fixtures
(`gcd1m`, `prime_count`, `popcount`, `mandelbrot`, `collatz`) declare
top-level scalar counters that hit the same Phase K.3 promotion path
and were paying the same memory-dance penalty. A follow-up phase-close
5-pass run on the full bench matrix will quantify the per-fixture
improvement.

### Why this didn't surface earlier

The Phase K.3 promotion rule was correct for **named-fn cross-references**
(top-level `let X` that's read from a fn body needs a stable address)
but accidentally caught **main-only counters** too. LLVM's default
linkage for `m.add_global(...)` is external — without an explicit
`set_linkage(Internal)` call, the symbols looked observable to LTO,
forcing conservative DSE behavior. The fix is a one-line per type-branch
addition.
