## Surface taxonomy

### Bucket A — Rust std internal (12 symbols)

Pulled in transitively by `std::sync::Mutex` / `std::io` /
`std::panic` infrastructure that some Layer-1+ Rust sub-crates
still use:

- `_malloc`, `_free`, `_realloc`, `_posix_memalign` — Rust's
  system allocator default. Even with our `__torajs_libc_malloc`
  shim used by sub-crate `#[link_name="..."]` declarations,
  Rust std's own allocator (`std::alloc::System`) bypasses our
  shim and calls libc directly.
- `_pthread_mutex_*` (7 symbols) — `std::sync::Mutex` lock
  implementation on macOS. Used by:
  - `torajs-collections/probe.rs` (Mutex<Vec<usize>>)
  - `torajs-str` (small-Str pool TEST_LOCK + COMPILE_LOCK)
  - misc test infra in `#[cfg(test)]` paths
- `__tlv_bootstrap` — Rust's thread-local storage runtime.
  Used wherever a `#[thread_local]` static or `std::thread_local!`
  macro appears in the staticlib chain.

**Cause**: Layer-1+ crates aren't `#![no_std]`. Switching them
involves:
1. Replacing `std::sync::Mutex` with a futex-based mutex (Linux)
   / `os_unfair_lock` (macOS via `objc::msg_send!`-style FFI,
   or raw syscall).
2. Replacing thread_local with a fixed-array indexed via
   GS/FS-reg lookup (or accept single-thread limit for v0.7).
3. Setting `#![no_std]` + providing a panic_handler per crate.
4. Replacing `std::alloc::System` with `torajs-mmalloc`'s
   global allocator via `#[global_allocator]` annotation.

### Bucket B — LLVM/Rust intrinsic fallbacks (3 symbols)

LLVM emits `memcpy` / `memcmp` / `memmove` for `core::ptr::copy_*`
operations + Rust's `[u8]::copy_from_slice`. The Rust
`compiler_builtins` crate provides these as fallbacks; LLVM
inlines short copies but falls through to the symbol for
unbounded loops.

**Cause**: Standard codegen pattern. Even no_std crates pull
these from `compiler_builtins`.

**Fix path**:
1. Provide `__torajs_memcpy` / `__torajs_memcmp` / `__torajs_memmove`
   in torajs-syscall (or a new torajs-mem crate) that satisfy
   the symbol — Rust's linker resolves the compiler-emitted
   reference against the first matching symbol.
2. Implement via the LLVM intrinsic name pattern: `#[no_mangle]
   pub extern "C" fn memcpy(...)` so Rust's linker accepts our
   implementation as the libc-shape symbol.

### Bucket C — IO / error / panic glue (3 symbols)

- `_write` — Rust's `std::io::stdout()` + std::io::stderr() use
  this. Also pulled by `torajs-panic-runtime`'s direct
  `extern "C" fn write(...)` declaration even though that's a
  redundant declare (already provided by torajs-syscall as
  syscall trampoline).
- `_strlen` — used by Rust std's c_str / cstring conversions
  (panic-handler message formatting, eprintln!, etc.).
- `_strerror_r` — used by Rust std's `std::io::Error::last_os_error`
  → `Display`. Pulled in panic backtrace code.
- `_abort` — explicit `abort()` calls in some panic-runtime
  paths; also LLVM's `__rust_alloc_error_handler` fallback.

**Cause**: Rust std's io::stderr-write + Display impls.

**Fix path**: Same as Bucket A — go no_std + provide our own
panic_handler that writes via `torajs-syscall::write(2, ...)`
and aborts via the raw `exit` syscall.

## Design — A 轴 close substrate path

### Step 16-a: torajs-mem crate (Bucket B)

NEW crate `torajs-mem` with:

```rust
// crates/torajs-mem/src/lib.rs
#![no_std]

/// memcpy(dst, src, n) — overlap-safe forward copy.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn memcpy(dst: *mut u8, src: *const u8, n: usize) -> *mut u8 {
    // Rust-side byte-by-byte loop; LLVM auto-vectorizes
    // to NEON for amd64-host / aarch64-host targets.
    // Fall through to compiler_builtins' bulk-copy on
    // very large n.
    ...
}

#[unsafe(no_mangle)]
pub unsafe extern "C" fn memmove(dst: *mut u8, src: *const u8, n: usize) -> *mut u8 { ... }

#[unsafe(no_mangle)]
pub unsafe extern "C" fn memcmp(a: *const u8, b: *const u8, n: usize) -> i32 { ... }
```

Linked into the staticlib chain via `TORAJS_STATICLIBS` so the
linker resolves the compiler-emitted `memcpy` reference against
our symbol before it falls back to libSystem.

Acceptance: `nm /tmp/<bin> | grep -cE "memcpy|memmove|memcmp" `
returns 0 (or returns matching definitions, not undefined refs).

### Step 16-b: torajs-mutex crate (Bucket A — pthread)

NEW crate `torajs-mutex` providing a `Mutex<T>` API that
matches `std::sync::Mutex`'s shape, backed by:

- macOS: `os_unfair_lock` (FFI to `libobjc` is NOT acceptable
  per 0-libc goal — instead use `__ulock_wait` / `__ulock_wake`
  raw syscalls; same kernel primitives `os_unfair_lock`
  internally uses).
- Linux: futex syscall via `torajs-syscall`.

Replace every `std::sync::Mutex<T>` use in Layer-1+ sub-crates
with `torajs_mutex::Mutex<T>`. Audit shows ~4 sites
(torajs-collections probe.rs, torajs-str pool sites,
torajs-throw error registry).

Acceptance: `nm /tmp/<bin> | grep -cE "pthread_mutex"` == 0.

### Step 16-c: no_std rollout (Bucket A — std)

Walk each Layer-1+ sub-crate that currently uses std types
(`Vec`, `String`, `HashMap`) and switch to no_std + alloc-only
(`alloc::vec::Vec` etc. via `extern crate alloc;`). Provide
a panic_handler per crate that writes via torajs-io to stderr
and aborts via raw exit syscall.

Affected crates (rough audit, will refine when shipped):
- torajs-collections (uses HashMap via std)
- torajs-str (uses std::sync::Mutex + std::thread_local)
- torajs-throw (uses std for error registry)
- torajs-num (uses core only — already no_std-friendly)
- torajs-arr (uses core only — already no_std-friendly)
- torajs-fmt (already mostly no_std-clean; needs #![no_std] + alloc handler)
- torajs-io (already no_std)
- torajs-syscall (already core-only; #![no_std] deferred)

Acceptance: `__tlv_bootstrap` + Bucket-C symbols disappear.

### Step 16-d: Global allocator wiring

```rust
// somewhere in torajs-core or a dedicated torajs-alloc crate
#[global_allocator]
static GLOBAL: TorajsAllocator = TorajsAllocator;

struct TorajsAllocator;
unsafe impl core::alloc::GlobalAlloc for TorajsAllocator {
    unsafe fn alloc(&self, layout: core::alloc::Layout) -> *mut u8 {
        unsafe { __torajs_libc_malloc(layout.size()) as *mut u8 }
    }
    unsafe fn dealloc(&self, ptr: *mut u8, _layout: core::alloc::Layout) {
        unsafe { __torajs_libc_free(ptr as *mut core::ffi::c_void) }
    }
}
```

Forces Rust's `Vec` / `Box` / `String` to use mmalloc instead of
the system allocator. Removes `_malloc` / `_free` / `_realloc`
/ `_posix_memalign` from the user binary's undefined symbols.

Acceptance: `nm | grep -E "^[ ]+U _(malloc|free|realloc|posix_memalign)"`
== 0.

## Why this is "正统"

- **`os_unfair_lock` raw syscall** is the textbook macOS sync
  primitive (used by std::sync::Mutex internally on macOS).
  Calling `__ulock_wait` / `__ulock_wake` directly is the same
  kernel primitive without the libc wrapper.
- **Custom global allocator** is a standard Rust pattern
  (`#[global_allocator]` is the canonical way to redirect
  std::alloc::System).
- **memcpy/memmove/memcmp as #[no_mangle]** is exactly how
  compiler_builtins exposes them; our torajs-mem just provides
  a different implementation under the same symbol.
- **no_std rollout** is the standard pattern for kernel /
  embedded / metal-tier crates; mirrors how `tokio` /
  `tracing` ecosystems handle their `default-features = false`
  paths.

## ROI estimate

- **Binary size**: removing libSystem.B.dylib reference saves
  ~50 KB of dyld stub overhead per binary. Larger savings if
  ALL Rust std infra (panic machinery, fmt::Display chain) is
  stripped — could be 200-500 KB.
- **Startup time**: dyld loading libSystem at process start
  takes ~5-20 ms (cold dyld cache; warm cache: ~0.5-2 ms).
  Direct staticlib binaries skip this entirely → measurable
  speedup on `startup` fixture.
- **Vision #4 (0 deps)**: this is the final substrate ship that
  achieves the "user binary has no external dependencies"
  vision goal. After A5, the tr-built binary is a single
  self-contained Mach-O / ELF artifact with only kernel
  syscalls as external boundary.
- **Vision #1 (perf)**: minimal direct impact; the perf gains
  are second-order (startup time + dyld cache eviction
  pressure).

## Step 16-d ship — out-of-order from original ladder

**Original assumption** (audit @ `9218ded`): 16-d ("global
allocator wiring") was blocked on 16-c ("no_std rollout") because
the allocator was thought to need a no_std-compatible context.

**Re-audit @ HEAD `27e571c`** (during 16-d hotify) showed:

- torajs-mmalloc was already complete: page bump + size-class
  free list + large mmap fallback + TLAB + central queue +
  span registry + Layer 1 sized API (`__torajs_malloc / _free /
  _realloc / _calloc`) + Layer 2 libc-compat shim with
  SHIM_HEADER (`__torajs_libc_malloc / _free / _realloc /
  _calloc`).
- ssa_inkwell `declares.rs` was already cutover: every IR-
  emitted `call malloc / call free / call realloc / call memcpy
  / call memmove / call memcmp` resolves to the `__torajs_libc_*`
  staticlib symbol (not to libc directly).
- The single remaining gap was the **Rust-side** `__rust_alloc /
  __rust_dealloc / __rust_realloc / __rust_alloc_zeroed` shim
  — Rust std's `Box::new / Vec::push / String::from` fall
  through to `std::alloc::System -> libc malloc/free/realloc/
  posix_memalign` unless a `#[global_allocator]` static is
  declared somewhere in the user binary's staticlib chain.
- That static does not need a no_std context. It just needs to
  exist in exactly one staticlib that ends up on the link line.

**Implementation** — single-marker site in `torajs-panic-runtime`
active mode (`#[cfg(torajs_panic_runtime_active)] mod active`):

1. `torajs-panic-runtime/src/lib.rs` declares `static GLOBAL:
   TorajsAllocator = TorajsAllocator; #[global_allocator]` inside
   the active `mod`. Why this crate: it is `-Wl,-force_load`-
   first per `ssa_inkwell/panic_runtime_link.rs`, so its
   `__rust_alloc_*` shim wins the link-order race against any
   sibling staticlib that emits a default-System fallback.
2. The GlobalAlloc impl extern-routes to
   `__torajs_libc_malloc / _free / _realloc` (exported by
   torajs-mmalloc) — link-level binding, preserves panic-runtime's
   "0 Cargo deps" invariant.
3. Alignment contract: `Layout::align() <= 16` routes directly
   (SHIM_HEADER guarantees 16-byte align); for larger align we
   over-allocate `size + align - 1 + sizeof(usize)`, store the
   raw base in a one-`usize` pre-header, return an aligned ptr.
4. `torajs-mmalloc/src/global_alloc.rs` keeps the GlobalAlloc
   impl as a reference (now-unused, but the trait math is reused
   for documentation + future flexibility) — the `#[global_allocator]`
   marker is deleted from here.

**nm verification** (`tr build /tmp/check_libc.ts -o /tmp/check_libc`
on HEAD `2c6a29d`):

```

malloc family:    5 ->  0   (_malloc / _free / _realloc /
                              _posix_memalign / _calloc gone)

dropped alongside (Rust std's path/io/error/backtrace tree
dead-strips once alloc no longer pulls libc):
  ___error / __dyld_get_image_* (4) / __Unwind_* (10) /
  _bzero / _close / _closedir / _dirfd / _dispatch_* (4) /
  _fstat / _getcwd / _getenv / _mmap / _munmap / _open /
  _opendir / _pthread_threadid_np / _readdir_r / _writev

residual 11 undef (next ladder targets):
  __tlv_bootstrap   (Rust TLS — needs no_std rollout, 16-c)
  _abort            (Rust panic_runtime fallback — drop via
                     syscall_exit shim, 16-c)
  _pthread_mutex_* (7)  (std::sync::Mutex — 16-b)
  _strerror_r       (std::io::Error::last_os_error — 16-c)
  _write            (Rust std stdout / stderr — 16-c)

libSystem.B.dylib still referenced (needs the 11 residuals
dropped before otool -L clears).
```

**Link warnings**: `ld` reports one duplicate-symbol warning
for `__RNvCs...___rustc12___rust_alloc` between libtorajs_panic_runtime
and libtorajs_syscall. Cause: `build-std` rebuilds alloc crate
inside every staticlib, so each emits the alloc shim — sibling
crates emit the default-System fallback, panic-runtime emits
the GlobalAlloc routing. Linker resolves to the `-force_load`-
priority panic-runtime version; routing is correct. Warning
disappears after 16-c rolls sibling crates to `#![no_std]` (so
they stop pulling alloc).

**Why this is "正统"** (per design pillar #3):

- `#[global_allocator]` is the **canonical Rust** way to
  redirect std::alloc::System. Rustc-book § "Custom allocator"
  is the reference; this commit follows the textbook pattern
  exactly.
- Single-marker site is the **rust-lang convention**: e.g.
  `mimalloc-rs / jemallocator / tikv-jemalloc-ctl` all put the
  GlobalAlloc marker in one crate and declare `#[global_allocator]`
  in the consumer's `main.rs` / `lib.rs` once.
- Routing via link-level `extern "C"` (instead of Cargo dep)
  preserves panic-runtime's "0 Cargo deps" invariant — same
  pattern as torajs-collections / torajs-promise / torajs-weak
  using `#[link_name = "__torajs_libc_malloc"]` extern blocks.

**Why this is "上限性能"** (per design pillar #1):

- All Rust std allocations now hit torajs-mmalloc's TLAB fast
  path (~3 cyc push, ~1-2 cyc TLS load) instead of libc's
  thread-cache miss + size-class lookup.
- Drops the ~5-20 ms cold dyld load of libSystem (will measure
  after 16-b + 16-c finish dropping the last 11 syms).
- Eliminates malloc's per-alloc lock contention (libc system
  malloc uses a global arena Mutex on macOS); torajs-mmalloc's
  TLAB + CentralQueue is lock-free MPMC.

torajs +12% vs bun-aot +16% = +4pp gain. These case-level
shifts net to a -0.43× geomean drag against bun-aot's wall-time
envelope.

**Gate verdict**: vs rust MET (primary perf indicator per
design pillar #1 "performance-first; run_ms primary metric");
vs bun-aot near-MISS attributed to mac thermal envelope on a
single-pass 5-run bench (single-run noise is ±20-40% on mac;
5-run median is ±5-10%; observed -0.108× = -2.6% of 4.10× gate
sits inside the noise window). **No trigger lowering** per
`feedback_no_trigger_lowering`. If subsequent ships (16-b,
16-c) show vs bun-aot consistently below 4.10× across multiple
bench sessions, the allocator-routing overhead is real and
needs root-cause (likely small-object alloc path now pays
SHIM_HEADER + size_class lookup cost in TLAB miss path that
libc malloc's thread-cache was absorbing).

**Surface accepted**: 16-d substrate is correct + 正统; perf
substrate-neutral within thermal envelope. Phase A5 continues
to 16-b (mutex) next.

## Step 16-b ship (`088b1f9` + `4f6ea7e`)

**16-b-1 substrate** (`088b1f9` — NEW crate scaffold):

NEW `crates/torajs-mutex/` (lib + staticlib). 314 prod LOC + ~200
test LOC. Three-state futex mutex (Drepper) backed by macOS
`__ulock_wait` / `__ulock_wake` raw syscalls (XNU sysno 515 / 516).
`UL_COMPARE_AND_WAIT = 1` flag (futex-shape, maps cleanly to Linux
futex(2) when that backend ladders later).

```rust
pub struct Mutex<T: ?Sized> {
    state: AtomicU32,     // 0=unlocked, 1=locked, 2=locked+waiters
    data: UnsafeCell<T>,
}

impl<T> Mutex<T> {
    pub const fn new(value: T) -> Self  // const for `static MUTEX:`
}

impl<T: ?Sized> Mutex<T> {
    pub fn lock(&self) -> MutexGuard<'_, T>          // no Result
    pub fn try_lock(&self) -> Option<MutexGuard<'_, T>>
    pub fn get_mut(&mut self) -> &mut T
}
```

12 unit tests in the crate (fast path stress 100k round-trips,
contended 2-thread × 10k iters, ulock_wait probe with brief
timeout, const_new static, etc.). All pass; 5/5 stable across
re-runs (one transient SIGSEGV on first parallel-tests run did

The handoff predicted `_write` came from `std::io::Stdout::write_all`.

### Mechanism — torajs-namespaced C-ABI exports

New `crates/torajs-syscall/src/extern_api.rs` (70 LOC):

- `#[unsafe(no_mangle)] pub unsafe extern "C" fn __torajs_syscall_write
  (fd: i32, buf: *const u8, n: usize) -> isize` — wraps
  `syscall3(SYS_WRITE, ...)`, returns raw `isize` (NOT a Rust Result),
  byte-compatible with the libc `write` signature the callers expect.
- `#[unsafe(no_mangle)] pub extern "C" fn __torajs_syscall_abort()
  -> !` — `kill(getpid(), SIGABRT)` then escalate to uncatchable
  `SIGKILL`, then `exit(134)` + spin loop as the noreturn guarantee.

`SIGABRT=6 / SIGKILL=9` added to `sysno.rs`; `pub mod extern_api`
(cfg aarch64-macos) added to `lib.rs`. Both caller crates swap their
extern block to `__torajs_syscall_*` and call the new symbols;
`torajs-abort` drops its now-dead `use core::ffi::c_void`
(panic-runtime keeps it — still used by the 16-d global_allocator
extern block).

Link-level bind: `libtorajs_syscall.a` is `STATICLIBS[0]`
(build.rs:95), present in every user binary, so the two undefined
refs resolve at final link exactly like 16-d's `__torajs_libc_malloc`.
**0 Cargo deps preserved** in both caller crates (link-level, not
Cargo-level). Never shadows the libc `write`/`abort` symbol names
(16-a-2 lesson, `feedback_libc_shim_caveat`).

### Why `__torajs_syscall_abort` raises SIGABRT (not bare exit(134))

The handoff suggested `syscall1(SYS_EXIT, 134)`. Research (web-verified
against musl `src/exit/abort.c`, glibc `stdlib/abort.c`, Go runtime
`signal_darwin.go`, Rust `std::process::abort` / PR #31457) confirmed
**every reference libc raises SIGABRT**, never synthesizes the exit
code. `134` is the shell's wait-status encoding (128 + SIGABRT(6)) of
a signal-death, not a value `abort()` passes to `exit`. Delivering a
real SIGABRT preserves core-dump / lldb-attach / `WIFSIGNALED`
semantics that a bare `exit(134)` permanently discards (ceiling-first).
The SIGKILL + exit(134) tail is the `-> !` soundness fallback (SIGABRT
is catchable/blockable/ignorable; torajs installs no handler today so
the first kill terminates, but a noreturn fn must guarantee it).

## Step 16-c-3 ship (`6d3f19f`) — Math.random 0-libc seed via getentropy(2)

Discovered during 16-c-2 verification: a `Math.random()` user binary
still pulled 5 libc symbols that a minimal binary (undef 0) did not.
A/B against the minimal binary localized all 5 to a single root cause —
`seed_rng_state()` calling `std::time::SystemTime::now()` to seed the
xorshift128+ generator. `SystemTime::now()` on macOS drags in
`clock_gettime` (the time syscall), `__error` + `strerror_r` (libc
errno path), and `memset` / `bzero` (std::time struct zeroing).

### Design — getentropy over gettimeofday/commpage

Ceiling-first choice for an RNG seed: `getentropy(2)` (BSD sysno 500,
SDK-verified from `<sys/syscall.h>`). It reads the kernel CSPRNG —
**the same crypto-quality entropy source V8 / SpiderMonkey use** — in a
single `svc`, no errno-heavy libc wrapper. JS spec leaves the
Math.random seed "implementation-defined", so any non-degenerate seed
is conformant; crypto-quality > wall-clock time (higher entropy, no
time-correlation predictability). `gettimeofday` (sysno 116) would also
drop the libc syms but gives a weaker, predictable seed; the commpage
fast-path is fragile/private. getentropy wins all five pillars.

### Changes

- `crates/torajs-syscall/src/sysno.rs` — `SYS_GETENTROPY = 500`.
- `crates/torajs-syscall/src/safe.rs` — `getentropy(buf) -> Result<(),
  Errno>` (svc via `syscall3`, decode negative-errno). 2 tests: 16-byte
  draw is non-zero + two draws differ; >256 returns an error (errno
  value left unasserted — macOS returns EINVAL=22, the man page
  documents EIO, so we only assert non-zero).
- `crates/torajs-syscall/src/lib.rs` — re-export `getentropy`.
- `crates/torajs-num/{Cargo.toml,src/math.rs}` — add torajs-syscall path
  dep (workspace crate, 0 external deps); `seed_rng_state()` fills a
  `[u8; 16]` via getentropy → two u64 seeds. Defensive splitmix-of-
  constant fallback if getentropy ever fails (can't on a healthy kernel
  for 16 bytes).

## Step 16-a-3 audit — in-house memset / bzero feasibility vs the 16-a-2 revert

Goal of this step (docs-only, no substrate): decide **whether** and
**how** to give tr-built user binaries an in-house `memset` / `bzero`
so the Math.random binary's `nm -u` residual drops from 2 to 0 — without
repeating the 16-a-2 conformance break.

### (0) Methodology note — nm verification REQUIRES the active-mode tr

A plain `cargo build --release` `tr` does **not** produce 0-libc user
binaries. Re-verified this step: `target/release/tr` (plain cargo build)
linking a `Math.random` fixture yields **50+ undefined symbols**
(`_malloc _free _calloc _realloc _posix_memalign`, the full
`_pthread_mutex_*` family, `_abort _write _writev`, `_opendir _readdir_r
_closedir`, `_dyld_get_image_*`, `_bzero`, …) and `otool -L` still lists
`libSystem.B.dylib`. That binary is the panic-runtime **inactive** path
(ordinary Rust std link).

The "undef 5 → 2" result recorded for 16-c-3 was on a binary built by
`scripts/release-build.sh` (`--cfg=torajs_panic_runtime_active`), which
is the mode where tr force-loads the 0-libc staticlibs
(mmalloc 16-d / mutex 16-b / syscall 16-c) into the user binary. **All
16-a-3 nm acceptance MUST use the release-build.sh tr** — a plain
`tr build` will mislead (it shows `_bzero` but routes everything else to
libSystem, so it cannot confirm "2 → 0"). Recorded here because it is an
easy trap: the residual-2 claim is only reproducible in active mode.

### (a) 16-a-2 revert root cause — what actually broke

Source of truth: `feedback_libc_shim_caveat` memory + the "Acceptance
status" entry above. 16-a-2 is **not in git history** (it was a
working-tree experiment after 16-a-1 `strlen`, reverted before commit —
`git log --all | grep 16-a-2` is empty; the ladder jumps `27e571c`
strlen → `2c6a29d` 16-d).

What 16-a-2 added, in **one batch**: `bzero` **and** `abort` shims
together. Symptom on the conformance gate: ~30 fixtures
(class / instanceof / iterator / map / integration — the Rust-std
class-construction paths) **timed out at 60 s and were SIGKILLed**.
Zero explicit assertion failures — pure **hangs**, not crashes, not
wrong output.

Attribution: a hang (not termination) points strongly at `abort`. The
shim routed `abort()` straight to `torajs_syscall::exit(134)`, bypassing
libc `abort(3)`'s `raise(SIGABRT)` + signal-handler chain that Rust
std's panic / alloc-error / unwind infrastructure expects. When std
tried to abort during those fixtures, the signal-handler-aware unwind
could not complete → deadlock. **`bzero` was batch-reverted alongside
`abort`; its individual contribution to the hang was never isolated.**

### (b) memset safety judgment — almost certainly safe

`memset` was **never part of 16-a-2** (16-a-2 added bzero + abort). The
memory's "How to apply #3" groups memset with bzero as "UNSAFE in the
simple form", but that is an *inference by analogy to bzero*, not an
observed failure — memset has no negative evidence at all.

The positive case is strong and symmetric to the already-shipped
`memcpy`:

- LLVM lowers `@llvm.memset.p0.i64` exactly the way it lowers
  `@llvm.memcpy.p0.p0.i64` — both are leaf memory intrinsics with the
  same attribute shape (`argmemonly` / `willreturn` / `nounwind`, write
  exactly `n` bytes, no syscall / signal / control-flow effect).
- `memcpy` / `memmove` / `memcmp` / `strlen` shipped at `5cc3865` +
  `27e571c` with conformance **687 / 0 / 1** — a byte-loop leaf shim is
  provably compatible with the force_load path.
- A byte-loop `memset(s, c, n)` that writes `c as u8` `n` times is
  idiom-matched by LLVM into the same NEON `stp` store loop, with no
  semantic difference from libc memset.

**Judgment: memset is safe to shim.** Risk is the same low tier as
memcpy. Still gated by a full conformance run before ship (per the
caveat rule — every new `#[no_mangle]` libc shim runs the gate).

### (c) bzero safety judgment — uncertain, needs isolated test; workaround if it fails

`bzero` is *also* a pure leaf byte op (`bzero(s, n)` ≡ `memset(s, 0, n)`,
returns void), so on first principles it should be as safe as memset.
The only evidence against it is its presence in the 16-a-2 batch — which,
per (a), is **unattributed** because `abort` (the far more plausible hang
culprit) was reverted in the same batch.

There is one extra subtlety to resolve in substrate: on AArch64 the LLVM
backend can canonicalize a **zero**-fill `@llvm.memset(p, 0, n)` to a
`bzero` call while non-zero fills stay `memset`. If that is the origin
of both residual symbols, they come from the **same** intrinsic and must
be shimmed **together** — a memset-only shim would not drop `_bzero`
(the zero-fills still emit `bzero`). This is verifiable by disassembling
the active-mode binary's call sites (`otool -tV | grep -E 'bl _(bzero|memset)'`)
during substrate; it does not change the safety judgment, only the ship
sequencing.

**Judgment: bzero is probably safe but must be validated in isolation**
(without abort, which 16-a-2 conflated it with). The substrate step ships
bzero **alone** and runs the full conformance gate — that run finally
attributes the 16-a-2 failure:

- gate **passes** → bzero was innocent in 16-a-2; abort was the sole
  culprit. rand binary → undef 0. (Confirms the caveat memory's bzero
  entry was over-cautious; update it.)
- gate **hangs/fails** → bzero is genuinely unsafe under force_load.
  Fallback, in ceiling order:
  1. **Suppress LLVM bzero emission**: compile the staticlibs with
     `-Cllvm-args=-disable-bzero` / `-fno-builtin-bzero`-equivalent so
     the backend emits `memset(p,0,n)` instead, then the in-house memset
     covers it and `_bzero` disappears with no bzero shim at all. This
     is the cleanest — no risky shim, just steer codegen to the symbol
     we already own.
  2. Accept a 1-symbol residual (`_bzero`) on the Math.random binary and
     record it as a known A5 carry-over — **only** if (1) is infeasible.
     This is a takagi decision point, not self-decided.

### (d) ROI + ship plan

Residual is 2 undef syms on the rand binary (the last libc on the
Math-only path). ROI: completes the A-axis "Math.random binary → undef
0" milestone and removes the last LLVM-mem-intrinsic libc dependency,
the same class 16-a already closed for copy/move/cmp/len. Low LOC
(~2 × the memcpy.rs shape, ~60 LOC + tests). 上限优先: this is the
textbook leaf-shim path that 16-a already validated; no ceiling
compromise.

Ship as **two conformance-gated sub-steps** (split so the 16-a-2
batch-conflation never recurs):

- **16-a-3-a — memset**: add `crates/torajs-mem/src/memset.rs`
  (`#[unsafe(no_mangle)] pub unsafe extern "C" fn memset(s: *mut u8,
  c: i32, n: usize) -> *mut u8`, byte loop mirroring memcpy.rs) +
  register in `lib.rs` (`mod memset; pub use memset::memset;`) + 3-4
  cfg(test) tests. Pre-flight + release-build.sh tr + full conformance
  gate + active-mode nm check. Expected rand binary undef 2 → 1 (or 2 → 0
  if the backend routes zero-fills through memset too — see (c)).
- **16-a-3-b — bzero**: add `crates/torajs-mem/src/bzero.rs`
  (`bzero(s: *mut u8, n: usize)`, byte-loop zero-fill) + register + tests.
  This is the isolated bzero test that attributes 16-a-2. Full
  conformance gate is the gate. If it hangs → abandon the shim, take the
  (c) fallback #1 (codegen-suppress bzero), do **not** force the shim.

If 16-a-3-a already drives the binary to undef 0 (same-intrinsic case),
16-a-3-b becomes unnecessary — confirm via nm before writing it.

### Step 16-a-3 ship results (actual vs audit prediction)

- **16-a-3-a memset** (`a939a4d`): shipped as predicted (low risk,
  symmetric to memcpy). Active-mode Math.random binary nm -u **2 → 1**
  (`_memset` dropped, `_bzero` residual). Conformance **687 / 0 / 1** —
  zero regression. Confirms memset/bzero are distinct lowered symbols (a
  memset-only shim cannot drop `_bzero`).

- **16-a-3-b bzero** (`5363f29`): the audit's "ship bzero alone, let the
  gate isolate it" plan ran — and the first naive byte-loop attempt
  **failed the gate (532 / 155 / 1, 155 fixtures timing out at 60 s)**,
  matching the 16-a-2 symptom exactly. **But the root cause is not what
  the audit guessed** (it was not a force_load semantic hazard, and abort
  was not the sole 16-a-2 culprit). Disassembly of the failing `_bzero`:

  ```
  _bzero:
    cbz  x1, <ret>     ; n == 0 → return
    b    _bzero        ; else unconditional self-branch → infinite loop
    ret
  ```

  **Self-recursion via the compiler.** LoopIdiomRecognize folds the
  zero-store loop into `@llvm.memset(p, 0, n)`; that pass's
  self-recursion guard is *name-aware* and only protects a function
  literally named `memset`, so inside `bzero` it fires. The AArch64
  backend then lowers the zero-memset back to a `bzero` libcall — and we
  are *in* `bzero`. `memcpy` / `memset` escape because their idiom fold
  targets the **same-named** libcall (the guard catches it); `bzero`
  shares no name with `memset`, so the late backend rewrite is unguarded.
  This also explains why the trivial AOT rand binary never hung: its code
  path simply never calls `bzero` with `n > 0`.

  **Fix:** `bzero(s, n)` ≡ `memset(s, 0, n)`, so delegate to the
  already-safe, name-guarded in-house `memset` through a
  `core::hint::black_box` fn-pointer barrier. The barrier stops LTO from
  inlining `memset`'s loop back into `bzero` (which would re-form the
  zero-fill loop and re-trigger the trap). `bzero` compiles to an
  indirect `blr` to `memset` (disassembly-verified — no self-branch);
  `memset` keeps its NEON-vectorized zero-fill. Active-mode binary nm -u
  **1 → 0** (EMPTY). Conformance **687 / 0 / 1** at `5363f29` — the 155
  previously-hanging fixtures all pass.

- **Memory correction**: `feedback_libc_shim_caveat` listed bzero as
  unsafe-because-invasive. The real story is narrower and more
  actionable — bzero is *safe* as a shim, it just cannot be a raw
  zero-store loop on AArch64 (self-recursion). Any future zero-fill leaf
  shim must either delegate to `memset` behind a barrier or be written so
  LoopIdiomRecognize cannot fold it into a same-effect libcall it lives
  in.

**Finding: every Rust-sub-crate path is at nm -u 0; the lone residual is

`_malloc _free _realloc _posix_memalign`, `_pthread_mutex_*` (7),

`__tlv_atexit`, `_abort _write _exit _munmap _sigaltstack _pause

**Root cause.** `runtime_regex.c` (3059 LOC, still C — known-debt

`alloc`, not C-side `malloc()` calls; 16-b's `torajs-mutex` only replaced
*Rust* `std::sync::Mutex` sites, not C `pthread_mutex_*`. So the C regex
code's allocation + capture-group + replace machinery resolves straight
to libSystem. `/ab/.test()` stays at 0 because the boolean-only path
allocates nothing and touches none of that C surface; `.match()` /
`.replace()` build result arrays/strings and capture state, which is
where the C `malloc`/lock calls live. The `_dispatch_semaphore_*` /
`_sigaltstack` / `_pause` cluster is dragged in transitively with that
heavier C path.

**16-e is blocked on the C-runtime libc surface, not on any Rust crate.**
The remaining A-axis work to reach "nm -u 0 everywhere" is concentrated
in the C runtimes that still call libc directly — `runtime_regex.c`
first (largest, confirmed), then a sweep of the other `runtime_*.c`
files (promise/date came back 0 here, but each C runtime needs its own
nm check across its non-trivial paths). Two ceiling-ordered options for
the next ladder (a takagi-scoped planning decision, not self-decided —
it is a multi-step effort that reshapes the A-axis tail):

1. **Port `runtime_regex.c` → a Rust `torajs-regex` sub-crate** (the
   known-debt plan). Highest ceiling: the ported crate's allocations go
   through the same `#[global_allocator]` → mmalloc, its locks through
   `torajs-mutex`, and it inherits the 0-libc story for free. Large
   effort (3059 LOC C → Rust).
2. **Route the C runtime's libc calls through the in-house shims**
   (provide `malloc`/`free`/`pthread_mutex_*` C-ABI symbols from the
   force_load staticlibs so the C code self-binds them like 16-a/b/d do
   for the Rust side). Smaller effort, but keeps the C runtime — lower
   ceiling, and it is a stopgap until the port.

## Step 16-e correction ★ (2026-05-29, resume-session ground-truth)

**The "Step 16-e residual-path audit" section above is wrong about the
root cause.** It was written without `find`-ing the filesystem and
asserted regex is "still 3059 LOC C (`runtime_regex.c`), port not done".
A ground-truth sweep this session (filesystem + `git log`) refutes that:

- **`runtime_regex.c` does not exist.** It was deleted in commit
  `e481e99` ("P6.2-e / closer ★: full RegExp + extern API cutover; nuke
  runtime_regex.c"). The only `.c` left under `crates/` is
  `runtime_libc_bridge.c`.
- **regex is already a complete Rust crate** — `crates/torajs-regex/`
  (26 `.rs` files: recursive-descent parser, Thompson-NFA compiler,
  Pike-VM matcher, replace/split/matchAll/exec, full `extern "C"` API
  `__torajs_regex_compile/test/find/drop` + `__torajs_str_replace_regex`
  …). Port ladder P6.2-a → closer all shipped, plus P9.3/P9.4/P9.5
  feature commits + `d6332e8` polish. It is in `build.rs`'s STATICLIBS
  list (`torajs_regex`, line 113), linked into every active user binary.
- **So Option 1 ("port C → Rust") is already done; Option 2 ("keep C
  runtime + shim") is moot — there is no C runtime to keep.**

**Real root cause of the 26 undefs** (re-measured this session with the
active-mode `release-build.sh` tr on `"aaa".replace(/a/g,"b")` — 26 undef
confirmed): `torajs-regex` is **not `#![no_std]`** (grep: zero matches;
it is a default-std crate). Its `.match()`/`.replace()` code paths reach
std-runtime entry points (`regex/mod.rs:160 std::process::exit`,
`replace_fn_dispatch.rs:284 std::process::abort`, plus `eprint!/eprintln!`
std-io), which pull in the whole std machinery — `std::sync::Once`
(`_dispatch_semaphore_*` 4 + `_pthread_mutex_*` 7), TLS (`__tlv_*` 2),
panic landing (`_sigaltstack _abort _exit _pause _munmap`), io
(`_write _strerror_r ___error`), and the std allocator path
(`_malloc _free _realloc _posix_memalign` — std's `System` allocator
bypassing the 16-d `#[global_allocator]` on this staticlib).

Contrast: `array` / `string` / `Date` paths use std crates too
(`torajs-num/arr/str` are also non-no_std) yet measure nm -u **0** — their
code paths never reach a std-runtime entry, so the linker dead-strips the
std machinery. regex differs only because it actively calls
`std::process::*` + `eprintln!`, which anchors std and defeats dead-strip.

**Corrected 16-e next step = no_std rollout of `torajs-regex`** (the audit's
own Bucket-A "16-c no_std rollout", applied to regex). Textbook path, 0-libc,
fully aligned with takagi's 2026-05-29 directive ("pure rust / metal / no C
runtime"). Mechanics (mirrors the already-no_std `torajs-fmt` / `torajs-mem`):

1. `#![no_std]` + `extern crate alloc;` at crate root.
2. `std::process::exit` → `torajs_syscall::exit`; `std::process::abort` →
   `__torajs_syscall_abort`.
3. `eprint!/eprintln!` → in-house stderr write (torajs-syscall write fd=2).
4. `format!/String/Vec/Box` → `alloc::`; `std::mem::swap` → `core::mem::swap`.
5. cfg-gated `#[panic_handler]` (mirror fmt/mem/syscall pattern; avoid
   duplicate-symbol across staticlibs).

Acceptance: `"aaa".replace(/a/g,"b")` active-mode binary `nm -u` drops the
std-runtime cluster; conformance 687/0/1 unchanged; bun byte-parity held.

**Broader A-axis tail**: 6 crates are still std (`num / arr / mmalloc / str /
collections / regex`); only regex's path currently surfaces undefs, but each
is a latent 16-c no_std candidate. regex is the confirmed-first target.

## Step 16-e str no_std ship + holdout CLOSED ★ (2026-05-29, `baae383`)

The resume handoff framed this as "step 1 of a multi-crate chain
rollout": no_std-ify `torajs-str` first, expect it to drop *some* of the
26 `.replace(/g)` / `.match()` undefs, then continue through `rc /
dynobj / arr / collections / num / mmalloc` until the path reaches 0.

**Actual result reversed the plan's premise: torajs-str alone took the
match/replace path 26 → 0.** A single crate closed the holdout. The
chain-rollout the handoff designed (steps for the other 5 crates) is
**not needed for nm-u-0** — `str` was the dominant std crate that the
match/replace cross-tier path reached; once it stopped pulling
`std::io::LineWriter` + `OnceLock` + `pthread::Mutex` + TLS, the other
crates' std parts on that path either weren't reaching std runtime or
got dead-stripped.

### What shipped

Same no_std-staticlib pattern proven on regex (16-c):

- `#![no_std]` + `extern crate alloc` + `#[cfg(test)] extern crate std`,
  no custom `#[panic_handler]` (staticlib inherits the active
  panic-runtime's; cargo test pulls libtest + std handler).
- `std::io::stderr` (the lone stdio use, `__torajs_str_print_err` /
  console.error) → `write_stderr`, a raw `write(2)` syscall via
  torajs-syscall. The payload+newline is composed once (reusing the
  existing `format_print_err`) and emitted in a single atomic write.
- Mechanical `std::` → `core::` for `c_void` / `sync::atomic`;
  `std::alloc::{alloc,dealloc}` → `alloc::alloc::*` + `core::alloc::Layout`
  (symbol.rs); compiler-driven `use alloc::{...}` per module (prod + test).

**Structural blocker — the local `mod alloc` name collision.** torajs-str
(and torajs-arr / torajs-dynobj) carries a local `pub mod alloc` (the Str
heap-block module). `extern crate alloc` for no_std then hits E0260 (name
defined twice). The textbook no_std idiom is `use alloc::vec::Vec` with
`alloc` = the Rust crate, so the local module's occupation of the
well-known name is the smell. Root-caused by **renaming the local module
`alloc` → `block`** (core type is `StrBlock`), freeing `alloc` for the
crate — rather than the `extern crate alloc as rust_alloc` workaround
(which sprays `rust_alloc::` noise across every site and violates the
"规范" pillar). No external crate referenced `torajs_str::alloc` by full
path (top-level re-exports cover the FFI surface); ABI symbols are
`#[no_mangle]` so the rename is link-invisible. **The same rename is the
template for arr / dynobj when their turn comes.**

## Step 16-e time-path ship — `Date.now()` via `gettimeofday` syscall ★ (2026-05-29, `0f7493f`)

The re-scope above named the time path as 16-e's sole remaining nm-u
holdout. This step closes the `Date.now()` / `new Date()` half of it.

### Root cause (confirmed by nm)

`torajs-date::now_ms()` used `std::time::SystemTime::now()`. macOS has
**no `clock_gettime` syscall** — std routes `SystemTime` through the
libc commpage wrapper, which drags three undefined libc symbols into
every AOT user binary that reads the wall clock:

```
_clock_gettime   (the time read itself)
___error         (errno access by the libc wrapper)
_strerror_r      (SystemTimeError Display / error formatting)
```

A minimal `const t = Date.now(); console.log(t > 0 ? "y" : "n")`
fixture, built with the active-mode `release-build.sh` tr, showed
`nm -u` = 3.

### Fix — direct `gettimeofday` syscall

`SYS_gettimeofday == 116` (cross-referenced against the SDK
`<sys/syscall.h>`; unlike `clock_gettime` it *is* a real BSD syscall).
A new safe wrapper in `torajs-syscall::safe`:

```rust
#[repr(C)]
struct Timeval { tv_sec: i64, tv_usec: i32 }

pub fn gettimeofday() -> Result<(i64, i32), Errno> {
    let mut tv = Timeval { tv_sec: 0, tv_usec: 0 };
    let raw = unsafe { syscall3(SYS_GETTIMEOFDAY, &mut tv as *mut Timeval as i64, 0, 0) };
    decode(raw).map(|_| (tv.tv_sec, tv.tv_usec))
}
```

Layout note (matters — got it right against the SDK, not from memory):
`tv_usec` is `__darwin_suseconds_t` = **`__int32_t` (i32)**, not i64.
Under `#[repr(C)]` the struct is 8 (`tv_sec`) + 4 (`tv_usec`) + 4 tail
padding = 16 bytes, matching XNU's `user64_timeval` `copyout` layout
exactly. The kernel `copyout`s into our stack-local `timeval`; on
success XNU returns 0 (or echoes `tv_sec` via x0 on some kernels) —
both non-negative, so `decode` reads the authoritative value from the
struct. Because `decode` never touches libc `errno`, the syscall path
is inherently free of `__error` / `strerror_r` — the same reason
`getentropy` replaced `SystemTime` for `Math.random`'s seed (16-c-3).

`torajs-date::now_ms()` now calls `torajs_syscall::gettimeofday()` and
computes `tv_sec * 1000 + tv_usec / 1000`. `torajs-date` gains a
single workspace-crate dep (`torajs-syscall`); its 0-external-Cargo-dep
property is preserved.

Two unit tests lock the wrapper: `gettimeofday_returns_plausible_epoch`
(`tv_sec > 1_700_000_000`, which also proves the copyout layout is
correct — a wrong layout leaves the struct zero) and
`gettimeofday_monotone_nondecreasing` (two back-to-back reads don't go
backwards).

### Result

`Date.now()` user binary `nm -u` undefined libc syms **3 → 0**. Runs
correctly (`y`). Pre-flight ALL GREEN: workspace 0-warn / fmt clean /
torajs-syscall 13 test + torajs-date 13 test / file-size < 500 prod /

### Residual time-path tail — `_localtime_r` (step 6+, larger)

## Step 16-e `_localtime_r` audit + plan (next L3a — in-house TZif)

Audit of the residual `_localtime_r` (and its `mktime` sibling on the
setter path), with the substrate plan to drop both. No code change in
this section — it hotifies the next L3a ladder.

### Call sites (ground-truth)

Both libc time fns are isolated to `torajs-date/src/tm.rs:41-44`:

```rust
unsafe extern "C" {
    fn localtime_r(secs: *const i64, out: *mut Tm) -> *mut Tm;
    fn mktime(tm: *mut Tm) -> i64;
}
```

- `localtime_decompose(ms)` (`tm.rs:48`) → `localtime_r` — backs the
  **local getters** (`getFullYear` / `getMonth` / … in `getters.rs:136+`).
- `components_to_local_ms(...)` (`tm.rs:62`) → `mktime` — backs the
  **local setters** + `new Date(y,m,d,…)` component ctor (`api.rs`).

The UTC getters already go through pure-Rust `civil::civil_from_days`
(0-libc). So the entire libc dependency is "convert between a UTC
instant and the *local* wall clock", i.e. one missing primitive:

> **`local_utoff(utc_secs: i64) -> i32`** — the local zone's offset
> from UTC (in seconds, DST included) effective at that instant.

With that, `localtime_decompose` = `civil_from_days((secs + utoff) / 86400)`
+ time-of-day split (all existing pure-Rust), and `components_to_local_ms`
= `days_from_civil(...) * 86400 + tod - utoff` with a two-pass DST
refine (textbook `mktime`: guess utoff from the local-as-UTC instant,
then re-query at the corrected instant — handles spring-forward gaps /
fall-back overlaps the way POSIX `tm_isdst = -1` does).

### Data source (ground-truth)

macOS ships IANA tzdata as TZif files. `/etc/localtime` is a symlink to
the active zone (verified: `→ /var/db/timezone/zoneinfo/Asia/Tokyo`);
its first 5 bytes are `TZif2` (`54 5a 69 66 32`) — RFC 8536 version-2
format. Read it with a direct `open` / `read` / `close` syscall (no libc
`fopen`). `SYS_OPEN = 5` / `SYS_CLOSE = 6` / `SYS_READ = 3` already exist
in `sysno.rs`; `read` already has a safe wrapper, `open` / `close` do
not yet.

### TZif v2 parse (RFC 8536, minimal subset)

A v2 file = [v1 block we skip] + [v2 header] + [v2 body]. We only need:

- header counts (`isutcnt`/`isstdcnt`/`leapcnt`/`timecnt`/`typecnt`/`charcnt`)
- `timecnt` × `i64` transition times (big-endian, seconds since epoch)
- `timecnt` × `u8` transition-type indices
- `typecnt` × `ttinfo { utoff: i32 BE, isdst: u8, desigidx: u8 }`

`local_utoff(t)` = binary-search the transition times for the last one
`≤ t`, take its type's `utoff`; before the first transition use the
first non-DST `ttinfo` (RFC 8536 fallback). The trailing TZ-string
(post-last-transition POSIX rule) is a later refinement — current IANA
data has transitions well past any date JS Date will see, so the v1
ladder ships without it and logs the cap.

### Plan (hotified L3a steps)

1. **torajs-syscall: `open` / `close` safe wrappers** — mirror the
   `read` wrapper (`syscall3` / `syscall1` + `decode`). Acceptance:
   unit test opens `/etc/localtime`, reads 5 bytes, asserts `== b"TZif2"`,
   closes; `cargo test -p torajs-syscall` 0 fail, 0-warn.
2. **torajs-date: new `tz.rs` module** — read `/etc/localtime` into a
   fixed buffer + TZif-v2 parser + `local_utoff(i64) -> i32`. File ≤ 500
   prod (split if needed). Acceptance: unit test asserts the host-zone
   offset for a known instant is a plausible whole-minute multiple in
   `[-50400, 50400]` (±14 h); round-trips across a transition.
3. **tm.rs cutover** — drop the `extern "C" { localtime_r / mktime }`
   block; reimplement `localtime_decompose` / `components_to_local_ms`
   on `tz::local_utoff` + existing `civil`. Acceptance: existing
   `localtime_round_trip_smoke` + `tm_struct…` tests still pass (the
   `Tm` struct stays as the getter return shape); `cargo test -p
   torajs-date` 0 fail.
4. **active re-bake + nm + conformance** — `new Date(0).getFullYear()`
   fixture `nm -u` = 0 (from 1); full local-getter + setter sweep 0
   undef; conformance 687/0/1. This closes the time path → 16-e nm-u-0
   for all Date paths.

### Why in-house (not "keep libc localtime_r")

Per the metal / 自研 pillars + `feedback_no_trigger_lowering`: the
acceptance is nm-u-0, and `_localtime_r` is the last time-path holdout.
TZif parsing is textbook (RFC 8536) and bounded; it is not a foreign
idiom. UTC-only would be silent-wrong — JS `Date` local getters must
honor the zone. Estimated ~300-400 LOC across `tz.rs` + 2 small syscall
wrappers — a self-contained module in `torajs-date`, not a new crate.

### Shipped — time path CLOSED (`6cb608b` + `6d2356c`)

All four plan steps landed; `_localtime_r` (and `mktime`) are gone.

- **`6cb608b`** — `torajs-syscall` `open` / `close` safe wrappers
  (scaffold; `read` already existed). Tests open `/etc/localtime`,
  assert the `TZif` magic, ENOENT path. Conformance 687/0/1.
- **`6d2356c`** — new `torajs-date/src/tz.rs` (215 prod LOC): TZif-v2
  reader (read `/etc/localtime` via syscalls → parse 8-byte transition
  block → `local_utoff(utc_secs) -> i32`), bounds-checked throughout,
  with a **plain-static cache** (not `#[thread_local]`, per 16-c-2;
  single-threaded runtime) so getters don't re-read the file. `tm.rs`
  cut over: `localtime_decompose` = `tz::local_utoff` + `civil_from_days`
  + weekday-from-epoch; `components_to_local_ms` = `days_from_civil` +
  JS month-overflow normalization + **two-pass DST** offset subtraction.

**Result.** A full time-path fixture (`new Date(0).getFullYear()` /
`.getMonth()` / `.getDay()`, the `new Date(y,m,d,h,m,s)` component ctor
→ old `mktime` path, `Date.now()`) builds with active-mode tr at
`nm -u` = **0** (was 1: `_localtime_r`). It runs, and is **byte-equal
to bun** on real values (host TZ Asia/Tokyo):

```
new Date(0):            1970 0 1 4 9 0      (1970-01-01 09:00 JST, Thu)
new Date(2024,5,15,…):  2024 5 15 12 30 45
new Date(2020,13,1):    2021 1 1            (month overflow normalized)
new Date(1.7e12):       2023 10 15 7
```

Conformance 687/0/1 at `6d2356c`. **The entire Date time path is now
nm-u-0** — combined with the `Date.now` gettimeofday step above, no
Date / time path drags any libc symbol into the user binary.

DST correctness (spring-forward gap / fall-back overlap) rides on the
two-pass `mktime` and the transition-table binary search; the trailing
POSIX TZ-string (offsets past the last recorded transition) is the one
documented cap — not exercised by any date current JS code produces.
