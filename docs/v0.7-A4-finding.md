## Scope

A4 covers the **f64 → string** and **string → f64** ABI surface.
Both are libc dependencies that the user binary still pulls in.
After A4: only `write(2)` (already direct syscall via
torajs-syscall) and `__torajs_libc_*` (mmalloc shim, A5 scope)
remain as user-binary libc surface.

## Design — new `torajs-fmt` crate

### Crate scaffold

```
crates/torajs-fmt/
├── Cargo.toml
├── src/
│   ├── lib.rs       — pub use dtoa::*; pub use atod::*;
│   ├── dtoa.rs      — Ryū f64 → string (preferred over Grisu3)
│   └── atod.rs      — Eisel-Lemire string → f64
```

### Algorithm choices

**dtoa: Ryū (Ulf Adams, 2018)** over Grisu3 / Grisu2 / dragon4

- **Why Ryū**: deterministic shortest-roundtrip in **one pass**
  (no try-precisions / round-trip verifier loop). Per Adams'
  paper: 2-3× faster than Grisu3 + handles edge cases (subnormals,
  ±0, NaN) without fallback. Same algorithm bun uses internally.
- **Why not Grisu3**: requires fallback to dragon4 on ~0.1% of
  inputs that fail the boundary check; adds complexity.
- **Why not snprintf-based try-precisions**: O(17) snprintf calls
  per print in the worst case; libc dependency; portability gap
  (subtle %g rounding differences across libcs).
- **LOC estimate**: ~500-700 prod LOC (Ryū's f64-to-string
  function + 1024-entry power-of-10 table + bit manipulation
  helpers). Smaller than Grisu3's ~800 LOC.

**atod: Eisel-Lemire (2020)** over hand-rolled strtod

- **Why Eisel-Lemire**: state-of-the-art fast-path string-to-f64
  parser (used by Rust std `f64::from_str`, simdjson). ~3-5×
  faster than strtod on the typical numeric token. Correct on
  100% of inputs (deterministic round-to-nearest-even).
- **Why not strtod port verbatim**: libc strtod's internal
  algorithm is complex (bigint mul + multi-precision compare);
  Eisel-Lemire is the modern equivalent that fits in fewer LOC.
- **LOC estimate**: ~800-1000 prod LOC (Eisel-Lemire core + 256-
  entry significand × power-of-10 table + slow-path bigint
  fallback for the ~0.0001% of inputs that don't fast-path).

## Why this is "正统"

- **Mainstream choice** — Ryū (used by bun, also citable per
  Adams' SIGPLAN '18 paper) + Eisel-Lemire (used by simdjson,
  Rust std `f64::from_str`, several modern JIT runtimes). Both
  are textbook PL-implementation choices.
- **Bun-parity acceptance** — byte-equal output is trivially
  provable on a finite fixture set; bun's own dtoa is also Ryū-
  based.
- **No silent-wrong risk** — algorithm correctness is well-
  studied; both have published proofs + reference implementations
  in multiple languages (C / Java / Go / Rust). torajs-fmt port
  is a translation, not a research project.
- **Single substrate boundary per cutover** — 15-d swaps every
  snprintf call site in one atomic commit; same dual-buffer
  rationale as Step 14-b/c (mixed snprintf + dtoa outputs would
  diverge on borderline inputs where libc and Ryū disagree on
  the shortest-roundtrip representation).

## ROI estimate

- **Perf**: Ryū is 2-3× faster than libc's `%g`-with-try-precisions
  on average f64. Print-heavy fixtures with f64 output
  (mandelbrot, ackermann's float branches if any, plus any
  f64-containing fixture) see direct speedup. Geomean impact
  ≈ +1-3% on vs-bun-aot ratio.
- **Binary size**: each user binary loses the libc `_snprintf` +
  `_strtod` dyld stub entries; saves ~100-200 B per binary. More
  importantly, after A5 the user binary may drop libSystem
  entirely (no libc imports at all), saving a multi-MB dyld
  resolve overhead at startup.
- **Correctness**: Ryū is shortest-roundtrip BY CONSTRUCTION; the
  current snprintf try-precisions loop is **stable but slower**
  and divergent across libcs (musl vs glibc vs Apple libc round
  edge-case f64 inputs differently). torajs-fmt eliminates that
  cross-platform drift.

## Step 15-d/e ship — atomic snprintf+strtod cutover — 2026-05-28

### Why atomic

Same cross-buffer rationale as Step 14-b/c: a partial cutover
would mix libc-formatted bytes with torajs-fmt bytes on the
print path. The two formatters disagree on shortest-roundtrip
edge cases (notably negative zero — my dtoa's first version
emitted "0" while libc snprintf "%.0f" emits "-0"; the
conformance run surfaced 4 fixtures with this exact pattern,
fixed in the same commit by preserving the sign at dtoa output).

### Cutover summary

**Rust call sites (5 sites across 4 sub-crates):**

| Crate | File | Replaced |
|-------|------|---|
| torajs-num | src/to_str.rs | f64_shortest %.*g try-precisions + strtod round-trip → `__torajs_fmt_dtoa` single call |
| torajs-num | src/to_str.rs | __torajs_i64_to_str snprintf("%lld") → `core::fmt::Write` via local `I64Writer` |
| torajs-arr | src/join.rs | f64 join element format → `__torajs_fmt_dtoa`; i64 join element → `__torajs_fmt_itoa` |
| torajs-arr | src/print.rs | f64 array print %g → `__torajs_fmt_dtoa` (now shortest-roundtrip instead of 6-sig-digit %g); i64 array print → `__torajs_fmt_itoa` |
| torajs-str | src/json_parse/parse_float.rs | strtod NUL-buffer-copy → `__torajs_fmt_atod` direct ptr+len |

**torajs-fmt extension:**

- NEW `src/itoa.rs` — `__torajs_fmt_itoa(n: i64, out_buf, out_cap)`
  via core::fmt::Write into stack buffer. 5 cfg(test) tests.
- `src/dtoa.rs` negative-zero fix: console.log(-0) preserves
  the sign per JS-spec Display; caller `__torajs_f64_to_str`
  post-strips for String() coercion per §22.1.3.6.

**torajs-core integration:**

- `TORAJS_STATICLIBS` + `build.rs` `STATICLIBS` add
  `libtorajs_fmt.a`. `COMPILER_SOURCE_FILES` already covers
  `ssa_inkwell/*` + `lib.rs` from the 14-b/c fingerprint fix;
  no per-fixture .o cache drift this time.

### Why the small perf regression

Rust `core::fmt`'s Grisu3 is mature + correct but slightly
slower than highly-tuned libc `snprintf("%g")` on the
common-case f64. Per-call overhead difference is ~50-100 ns;
print-heavy fixtures accumulate to a 2-3% geomean regression.

**This is an accepted A4 trade-off:** 0-libc dependency now,
hand-tuned Ryū port later (15-b' / post-A 轴 close polish).
The regained perf from a real Ryū port would push the geomean
back above 1.65× vs rust on the same fixtures. Per vision
priority order, #4 (0-deps) is currently load-bearing — the
2% cost is justified by removing two more libc symbols from
every tr-built user binary.
